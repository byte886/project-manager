# 并行调度与长任务守护

> 解决执行期的两个高频问题：①多任务怎么拆、怎么定并发（不是拍脑袋并行）；②单次运行超过 AI 后台任务时限的活怎么"跑着不丢、完了主动通知"。
> 与 [execution-ops.md](execution-ops.md) 的关系：execution-ops §二 管批量任务的断点/状态记录，§七 管"什么活适合并行/委托"；本篇管**并行怎么拆解调度、长任务怎么守护**，是它的动作层补充。
> 沉淀自真实批量流水线项目（2026-09 高顿课程自动化）；方法论通用，示例中的工具可替换。

## 一、大任务先拆 DAG，再谈并行

任何多阶段大任务先完整拆解为子任务节点并标注依赖（有向无环图 DAG），**不拆清楚不要并行**。

### 1.1 三种依赖模式

| 模式 | 含义 | 示例 |
|------|------|------|
| **Linear Chain** | A→B→C 顺序依赖 | 下载→压缩→转写 |
| **Fan-Out** | 一个完成触发多个并行下游 | 下载完成→OCR + 压缩并行 |
| **Fan-In** | 多个上游全部完成才触发一个下游 | OCR+转写+采集→知识库生成 |

### 1.2 每个节点必须标注

任务名、依赖、预估时长、资源类型（CPU/IO/API/交互）、最优并发度、状态。

### 1.3 产出物

项目 `docs/development/project-dag.md`（或放 `03_进行中的任务/`）：一页 DAG，列出节点与依赖，供执行期对照。小项目可不落盘，但拆解动作不能省。

## 二、实测定并发，不凭核数估算

**并发数 ≠ 吞吐提升**，CPU 密集任务尤其如此——单进程速度必然随并发下降，总吞吐可能不升反降。

### 反向评估四步

1. **先跑单进程基线**：记录单进程 CPU 占用、内存、速度（rtf 等）、单任务耗时。
2. **逐步加并发**：从 2 开始每次 +1（或跳测 3/6），每个并发度稳定运行 ≥3 分钟再采样。
3. **对比总吞吐**：`总吞吐 = 并发数 × 单进程速度`；单进程速度必然下降，关键看总吞吐是否上升。
4. **选总吞吐最高的并发度**：串行最高就用串行（反直觉但常见）。

实测案例（FunASR 转写，14 核）：串行单进程 18.5x 速度 = 总吞吐 18.5x（最优）；并发 2 时总吞吐反而降到 11.8x——**串行就是最优**。不要被"多核就该并行"带偏。

IO/API 类任务并发收益更高，但仍要实测（限流、风控、排队都是约束）；外部 API 限并发、保序、失败隔离，用 `mapLimit` 类原语。

## 三、事件驱动衔接，总调度实时决策

- 阶段间**用"完成事件"触发下游**，不靠固定 sleep 轮询。
- 需要一个总调度者（人或 AI 主控）持有 DAG 视图，实时决定：哪些节点可并行启动、哪些要等、卡住的重试还是降级。
- 执行中的状态写进批次状态文件（见 [execution-ops.md](execution-ops.md) §二），调度读状态、不猜状态。

## 四、长任务守护范式（单次运行 > 8 分钟）

### 4.1 为什么不能直接后台跑

AI 工具的 `Bash(run_in_background=true)` 后台任务存在约 **8 分钟超时**，到点被杀。数小时的任务直接后台跑会被反复终止，AI 只能定期检查重启——这是"轮询"，消耗轮次且依赖 AI 在线。

### 4.2 守护器范式（推荐）

```text
nohup 守护器（PPID=1，系统 init 接管，AI 会话结束也不影响）
  └─ while 循环：
       1. 执行任务脚本（断点续传，done 标记跳过已完成项）
       2. 执行完成检测命令
          ├─ 全部完成 → 系统通知（macOS osascript / 其它平台对应）→ exit 0
          ├─ 连续 N 轮进度无变化 → 异常通知 → exit 1
          └─ 否则 sleep 5 秒，进入下一轮
```

要点：
- **任务脚本必须断点续传**（done 标记/状态文件），守护器只是循环调用，重复执行幂等。
- **完成判定用命令检测**（如 `grep 完成标记`、文件数对账），不用"感觉差不多"。
- 异常判定：连续 N 轮进度无变化视为卡死，主动通知并退出。
- 通知通道：macOS 系统通知（`osascript -e 'display notification ...'`）、飞书消息等；让 AI 不轮询也能知道结果。

### 4.3 分层清理孤儿进程

守护器/父脚本被杀后，子进程可能被系统收养继续跑。停任务须分层：先杀顶层脚本 → 按特征杀孤儿子进程 → 再杀最底层工作进程；用进程组 PGID 排除当前 shell，连续两轮计数 0 才算根除。
