# 工程规范与过程件模板（standards / templates）

> 中大型工程项目进入执行期后，除了 docs/ 根的 5 个骨架文档（WORKFLOW / REQUIREMENTS / SYSTEM_REQUIREMENTS / DIRECTORY_STRUCTURE / DOCUMENTATION_MAP），还需要两类"常规文档"：
> - **规范层 `docs/project-management/standards/`**：命名、编码、文档写作、质量验证、状态查询、结构维护——回答"必须遵守什么"；
> - **过程件模板 `docs/development/templates/`**：任务报告、流程测试计划、验证报告、批量整改清单——回答"一次任务/一轮测试怎么留痕"。
>
> 本篇给这两类文档的**通用化模板**，从真实内容流水线项目提炼，已剥离业务专用内容，复制后按项目改造。
> 生命周期模板见 [templates.md](templates.md)，执行期台账/AGENTS/SOP 模板见 [templates-execution.md](templates-execution.md)。

## 启用建议（别一上来全搭）

| 项目规模 | 建议复制 |
|---|---|
| 小项目（1-2 周，单线程） | 不需要本文件任何模板；README + AGENTS + TASK_STATUS 足够 |
| 中项目（1-3 月，多任务、有代码） | SYSTEM_REQUIREMENTS、NAMING_CONVENTION、CODE_STYLE、DOCUMENTATION_GUIDE、任务报告模板 |
| 大项目（3 月+，批量处理、多平台、AI 长期协作） | 全套：再加质量验证、状态查询协议、结构维护、测试计划/验证/整改清单、CHANGELOG |

**原则**：规范是踩过坑后沉淀的，不是立项时拍脑袋写的。新建项目可先放占位（只建目录 + README 索引），跑到需要时再按本篇模板补；但 `docs/` 根 5 骨架建议工程立项时一次建齐。

## 2. NAMING_CONVENTION.md 模板（仓库工程命名规范）

> 解决"同一仓库里 kebab/snake/大写/中文混排、脚本名风格不一、找不到命名依据"的问题。
> 以下规则只规范 **Git 仓库内的工程文件**；业务数据/成品内容（如课程库、素材库）的命名由项目自定，可在本文档追加业务章节，但工程侧规则保持不变。
> **SSOT 原则**：命名规则只在本文档写一次，其它文档（CODE_STYLE、DIRECTORY_STRUCTURE、各 README）只引用不复述，避免多处写的阈值互相矛盾。

```markdown
# 目录与文件命名规范

> 文档类型：Governance（治理规范）
> 读者：AI 代理 + 开发者（新增/改名文件时必须遵守）

## 一、总原则
1. **先判性质，再定名字**：按第二节决策树判定，不凭"在哪个目录"或个人偏好。
2. **工程侧用英文，内容侧用中文**：给 AI/开发者看的规范、脚本、方法文档用英文；
   同步给最终读者的成品、每次任务产出的中文过程文档用中文，且文件名与一级标题（H1）语义对应。
3. **同职责文件风格一致**：禁止同一单词大小写混排、禁止中英文前缀混排。
4. **依据**：文件/目录名小写可规避"Linux 区分大小写、macOS/Windows 不区分"导致的跨平台问题；
   Python 模块名 snake_case 依据 PEP 8；连字符被搜索引擎视为词分隔符（Google 开发者文档风格指南）。

## 二、命名决策树（从上到下，命中即停）
1. 是平台/工具**固定名**？→ 走第三节白名单，原样不改。
2. 是**脚本**（.py/.sh/.js）？→ 全小写 snake_case（第四节）。
3. 是**面向读者的内容成品或中文过程产物**（H1 为中文）？→ 中文、与 H1 对应、日期用 ISO（第五节）。
4. 其余为**工程文档**（英文），再二选一：
   - 讲"必须遵守什么 / 标准是什么 / 供复制的模板 / 当前状态 / 清单索引"
     （规范、标准、模板、台账、索引、顶层骨架）→ 全大写 UPPER_SNAKE_CASE（第六节）；
   - 讲"怎么做一件事"（方法、操作、流程、工具/API 用法、最佳实践）→ 全小写 kebab-case（第七节）。
5. 架构决策记录 → `ADR-NNN-中文标题`（第八节）。
6. 目录 → 第九节。

> 最易混点：回答"规则/标准/状态是什么"用大写；回答"怎么操作、怎么做"用小写。
> 判型看正文实质（是强制标准还是操作教程），不看标题用词，也不看所在目录。

## 三、固定名白名单（原样不改，不得新造全大写固定名）
| 固定名 | 说明 |
|--------|------|
| `README.md` / `LICENSE` / `CHANGELOG.md` / `CONTRIBUTING.md` / `AGENTS.md` | 开源/社区约定名 |
| `.gitignore` / `requirements.txt` / `package.json` | 工具固定名 |
| `pre-commit` | Git hook 固定名，无扩展名 |
| `.github/` 及其下模板目录 | 平台固定路径，允许平台大写 |
| `.secrets/*.enc` | 加密凭证，主体名小写 snake |

## 四、脚本：全小写 snake_case
- 适用 `scripts/` 下 `.py/.sh/.js`：多词用下划线 `_`，**禁止连字符、禁止大写**。
- 正例：`fetch_data.py`、`check_directory_structure.sh`；反例：`fetch-data.py`、`FetchData.js`。
- 依据 PEP 8；唯一例外是 Git 固定名 `pre-commit`。

## 五、内容成品与中文过程产物：中文，文件名对应 H1
- **面向读者的成品**（整体可能 gitignore、同步到外部平台）：用读者语言命名，与外部节点/H1 对齐，如 `<知识点/章节原名>.md`。
- **每次任务产出的中文过程文档**（任务报告/测试计划/调研/整改方案）：
  统一格式 `{中文类型}_{对象}_{日期}.md`；日期用 ISO `YYYY-MM-DD`，禁止紧凑日期 `YYYYMMDD`，禁止中英前缀混排。
  - 正例：`任务报告_数据下载_2026-09-18.md`；反例：`REPORT_data_20260918.md`。
  - 无日期的持续性记录可省略日期段，如 `测试计划_<对象>.md`。

## 六、治理/规范/模板/台账/顶层骨架：全大写 UPPER_SNAKE_CASE
- 判定：回答"必须遵守什么、标准是什么、当前状态、供复制的骨架、清单索引"。
- 位置：`docs/` 根、`standards/`、`templates/`、`active/` 状态台账。
- 正例：`NAMING_CONVENTION.md`、`CODE_STYLE.md`、`REPORT_TEMPLATE.md`、`TASK_STATUS.md`。
- 模板统一以 `_TEMPLATE` 结尾；禁止同词大小写混排。
- **`docs/` 根顶层骨架文档固定大写**：`WORKFLOW / REQUIREMENTS / SYSTEM_REQUIREMENTS / DOCUMENTATION_MAP / DIRECTORY_STRUCTURE`，
  不随其内容类型改小写，与子目录里的具体方法文档（小写）形成层级区分。

## 七、方法/操作文档：全小写 kebab-case
- 判定：回答"怎么做一件事"，含步骤/流程/工具用法/API/最佳实践。
- 无论放在 `guides/api/tools` 还是其它目录，方法性文档一律小写连字符。
- 正例：`git-workflow.md`、`data-download.md`、`api-reference.md`。
- **H1 标题仍用中文**（文件名是中文标题的英文短名，语义对应即可）。

## 八、架构决策记录：ADR-NNN-中文标题
- 形如 `ADR-003-采用Parquet存储.md`：编号三位、连字符分隔、描述用中文；只增不改。

## 九、目录命名
- **工程目录**：全小写 kebab-case（`decisions/`、`standards/`、`guides/`），不用空格、不用大写；
  `.github/`、`.secrets/` 等隐藏/平台目录从平台约定。
- **内容/数据目录**：按业务体系命名（中文成品层可用中文，运行时工作区建议英文固定桶名）。
- 目录名与其中文件的命名风格相互独立：目录按本节，文件按第三~八节。

## 十、改名检查清单（新增/改名文件时逐项过）
- [ ] 命中固定名白名单？是则原样
- [ ] 脚本全小写 snake_case
- [ ] 中文成品/过程文档用中文、与 H1 对应、日期 ISO
- [ ] 治理/规范/模板/台账 UPPER_SNAKE；方法/操作文档 kebab-case
- [ ] 无大小写混排、中英前缀混排、空格、紧凑日期
- [ ] 改名用 `git mv` 保留历史，并级联更新引用、DOCUMENTATION_MAP、DIRECTORY_STRUCTURE
- [ ] 批量重命名/跨目录移动属 L1 高扩散变更：先出"老名/新名/依据/影响面"全量清单，确认后再执行（见 §8）
```

## 3. CODE_STYLE.md 模板（编码与文档风格规范）

> 从 AGENTS.md 中剥离"代码怎么写"的细则，保持 AGENTS 简洁。语言相关的具体规则（Python/JS/Shell）按项目技术栈填，本篇给骨架。

```markdown
# 编码与文档风格规范

> 文档类型：Governance（治理规范）
> 读者：AI 代理 + 开发者

## 一、脚本通用规范
- 所有可执行脚本统一放 `scripts/`，禁止散落在各业务子目录；一次性脚本用完即清（见结构维护规范）。
- Shell 脚本：`set -euo pipefail` 开头；注明兼容的 shell/版本。
- Python：加类型注解；函数式优先，避免可变全局状态；公共函数有 docstring。
- 文件名规则以 NAMING_CONVENTION.md 为唯一事实源（脚本 snake_case），本文档不复述。
- **产出落点受控**：脚本只把成品写到正式目录；运行数据写 `data/`、日志写 `logs/`、
  临时中转写系统临时目录或模块内 `.tmp_*/`，不得在业务目录散落缓存文件。
- **临时目录自清**：批处理脚本建的临时目录必须用 `trap ... EXIT` 兜底删除，
  保证正常/报错/Ctrl-C 都不留残；**断点续跑凭证例外，不得删**。
- 每新增一类运行产物，同步 `.gitignore`（如有 pre-commit 兜底检查也一并加规则）。

## 二、<主语言> 规范（按技术栈填写）
- 格式化工具：<black/ruff/prettier 及命令>
- Lint：<eslint/ruff/flake8 及命令>
- 关键约定：<导入排序、行宽、异常处理、日志用法、禁止硬编码路径等>

## 三、文档风格规范
- 统一 Markdown，标题层级 # → ## → ###，不跳级。
- 命令用代码块、路径用反引号、可执行命令完整给出（含参数与预期输出）。
- 每个文档开头标元信息头（文档类型/更新频率/读者），类型词表以 DOCUMENTATION_GUIDE.md 为准，不得自造。
- WORKFLOW.md 只放流程概览、校验门和链接，详细操作放专项 SOP，不重复。

## 四、提交前最小验证
- [ ] <格式化命令> 无 diff
- [ ] <lint 命令> 0 error
- [ ] 新增/改动脚本跑通过一次完整路径
- [ ] 涉及的测试通过（<测试命令>）
```

## 4. DOCUMENTATION_GUIDE.md 模板（文档写作指南）

> 规范"文档怎么组织、怎么分解、分几类、怎么写对 AI 友好"。是项目里所有文档的元规范。

```markdown
# 文档写作指南

> 文档类型：Governance（治理规范）
> 读者：AI 代理（写文档时必须遵守）

## 一、三层保障（重要规则别只埋在深文档里）
| 层级 | 位置 | 内容 |
|------|------|------|
| 第一层 | README.md / AGENTS.md 正文 | 核心规则、存储分工、禁止事项（每次读都能看到） |
| 第二层 | docs/ 子文档 | 详细步骤、参数、常见问题（按需深读） |
| 第三层 | 自动化（pre-commit / 检查脚本，可选） | 大文件、敏感信息、命名等机械项自动拦截 |

- 核心规则必须写进第一层，不能只放子文档链接；细节放子文档，README 放摘要和链接。
- 可自动化的机械检查尽量做成 hook/脚本，不依赖"记不记得读文档"。
- ⚠️ 自动化只拦机械项；内容过时、职责重复、台账与实际不符等语义项仍须人工体检（见 §5）。

### 动笔前先定落点（五类分工，避免过程件污染持久文档）
| 内容性质 | 落点 | 生命周期 |
|----------|------|----------|
| 活态台账（进度/问题） | `project-management/active/`（轻量项目放 `03_进行中的任务/`） | 高频改、常驻 |
| 稳定规范/方法论 | `docs/project-management/standards/`、`docs/development/` | 相对静态 |
| 不可逆决策 | `docs/project-management/decisions/ADR-NNN-*.md` | 只增不改 |
| 跨会话稳定结论 | `docs/project-management/memory/`（结论 + 相对指针） | 结论变才改 |
| 单次任务过程件（报告/测试计划/调研/草稿/一次性施工方案） | `data/_workspace/`（gitignore） | 任务完成即清/归档 |

**硬规则**：任务过程件不进 `docs/`、不入库；稳定、不可逆结论单向流入 ADR/工程记忆，
过程件只保留 `→ 见 ADR-NNN / concept xxx` 指针，不复制结论正文（双写必分叉）。

## 二、文档分解原则
**触发分解的信号**（满足任一）：
- 超过 **500 行**或阅读时间超过 10 分钟；
- 覆盖 **2 个以上独立专业领域**；
- 某子主题有独立的配置/参数/常见问题，可单独查阅；
- 某子主题频繁更新而其余部分很少变动。

**分解方式**：按专业领域分目录、按主题分文档；父文档只保留"总体流程 + 索引链接 + 一句摘要"；
每个子文档独立完整、可单独阅读。
- ❌ 反例：所有内容塞 WORKFLOW.md 超 1000 行；父文档只放链接不放摘要；子文档依赖父文档上下文才看得懂。

## 三、文档分类（Diátaxis 四分类 + 项目 7 类型词表）
按读者目的分四类，避免"什么都讲了但什么都不清楚"：
| 类型 | 读者目的 | 结构 |
|------|----------|------|
| 教程 Tutorial | 跟着做、学习 | 目标→前置→步骤→验证→常见问题 |
| 操作指南 How-to | 完成具体任务 | 问题→步骤→结果 |
| 参考 Reference | 查事实 | 参数表、配置项、命令说明 |
| 解释 Explanation | 理解概念 | 背景→原理→讨论→参考 |

每个文档主要属于一种类型；"怎么做"和"参数是什么"不要混在一篇。

### 文档类型标注（强制，封闭词表，不得自造）
每个文档开头必须标注：
> **文档类型**：Task（操作指南）/ Concept（概念说明）/ Reference（参考资料）/ Governance（治理规范）/ Active（过程记录）/ Knowledge（知识内容）/ Template（模板骨架）
> **更新频率**：<流程变更时 / 每月 / 按需>
> **维护者**：<AI 自动维护 / AI+用户审核 / 用户维护>
> **读者**：<AI 代理 / 人类 / AI+人类>

| 类型 | 说明 | 典型文件 |
|------|------|----------|
| Governance | 必须遵守的规则 | AGENTS、命名/质量/维护规范 |
| Task | 教你怎么做（方法、流程） | 下载指南、Git 工作流 |
| Concept | 解释是什么 | 架构说明、知识库组织说明 |
| Reference | 查事实 | 文档地图、API/参数参考 |
| Active | 做了什么、当前状态 | TASK_STATUS、任务报告 |
| Knowledge | 面向读者的知识内容 | 成品知识篇 |
| Template | 供复制的骨架 | `*_TEMPLATE.md` |

> 确需新增类型词，先改本词表（若有自动化白名单一并改），不得在单篇文档里自造。
> 原始素材、知识成品正文、过程报告可按规范豁免头部标注。

**类型 → 文件名风格映射**：Governance/Template/Active 台账/顶层骨架 → UPPER_SNAKE；
Task/Concept 方法文档 → kebab-case；Knowledge/中文过程报告 → 中文对应 H1。
完整规则见 NAMING_CONVENTION.md 决策树。

## 四、Docs as Code（文档即代码）
- 文档与代码同仓库、同版本控制；**改了脚本/流程必须同步改对应文档**（完成定义的一部分）。
- 过时文档比没有文档更危险（会误导）。
- **问题驱动更新（强制）**：发现文件位置不对、脚本有 bug、流程有缺陷、数据不一致时，
  立即评估：① 是否反映文档缺失/过时？② 改现有文档还是新增？③ 是否要补自动化检查？评估后必须执行。

## 五、定期梳理（每月或每个大任务后）
梳理清单：
| 检查项 | 方法 | 处理 |
|--------|------|------|
| 内容重叠 | 搜相同关键词是否在多处重复 | 一个主题只在一处详述，他处链接 |
| 冗余过时 | 查过时段落、重复章节、无用背景 | 删除/合并 |
| 事实错误 | 核对链接/参数/命令/路径 | 修正并验证 |
| 遗漏跳步 | 查流程完整性、参数缺失 | 补全 |
| 脚本说明 | 每个脚本在 scripts/README 有说明？ | 补用途/用法/依赖 |
| 链接有效 | 抽样/全量检查文档间链接 | 修断链 |
| 文档过大 | `wc -l`，>500 行且跨领域 | 按第二节分解 |
| 空目录/空标题 | `find . -type d -empty`；叶子标题下无正文 | 删除 |

统计命令：
```bash
find . -name "*.md" -not -path "*/.git/*" | wc -l
find . -name "*.md" -not -path "*/.git/*" -exec wc -l {} \; | sort -rn | head -10
```

## 六、AI 友好写作七原则
1. **答案在前**：每节开头先给结论/操作，再讲原因。
2. **短段落**：2-3 句一段，避免大段文字。
3. **标题反映问题**：用"如何配置 SSH"而不是"SSH 配置"。
4. **标题不跳级**：H1→H2→H3。
5. **命令完整可执行**：不只说"运行脚本"，给出完整命令和预期输出。
6. **参数用表格**：配置项、参数、选项用表格。
7. **明确"不要做什么"**：反例和禁忌比正面说明更重要。
```

## 5. 文档变更驱动与健康度检查模板（DOCUMENTATION_OPTIMIZATION.md）

> 两件事：① 新增/删除/移动文档后**必须联动改哪些文件**（变更驱动矩阵）；② 定期给文档体系做**健康度体检**。
> 提交前的轻量同步清单见 [templates-execution.md](templates-execution.md) §5；本篇是它的完整版 + 体检流程。

### 5.1 文档优化四步流程（做大改时遵守，禁止挤牙膏式逐步优化）

1. **先读最佳实践/元规范**（本篇、AGENTS 写作规范、对应类型文档的通行实践）。
2. **一次性全面分析**：列出所有不符合项（哪些内容别处已有→删了只链接；哪些是技术选择不是禁令→挪走；
   哪些是不言而喻的常识→删；哪些频繁变化→挪到活态台账；哪些是给人看的项目介绍→挪 README）。
3. **一次性执行全部修改**。
4. **改后主动对照验证**：遗漏项、新引入问题、篇幅、章节结构；不等用户指出问题。

### 5.2 变更类型 × 驱动动作矩阵（文档一变，自动触发，无需用户提醒）

| 变更类型 | 必须执行的联动动作 |
|----------|-------------------|
| **新增文档** | ① 先 grep 确认没有同类文档；② 更新 DOCUMENTATION_MAP；③ 需要则建新目录并更新 DIRECTORY_STRUCTURE；④ 在父文档/相关文档加链接；⑤ 重要架构决策评估是否补 ADR |
| **删除文档** | ① `grep -r "文档名" docs/ scripts/` 找全部引用；② 更新/删除引用；③ 更新 DOCUMENTATION_MAP；④ 删空目录；⑤ 评估 ADR；⑥ 持久文档删除走 §8 去留判据（先确认职责有承接方） |
| **移动文档** | 等同删除+新增：更新全部路径引用、MAP、DIRECTORY_STRUCTURE，验证链接有效 |
| **调整目录结构** | 先出方案（前后结构、移动路径、引用更新清单）→ 执行 → 全量更新引用/MAP/STRUCTURE → `grep -r "旧目录名"` 验证；重大调整记 ADR |
| **优化文档内容** | 内容搬走后原文改链接；同步他处对旧内容的引用；更新 MAP 中的说明；文档分解/合并属结构变更，评估 ADR |

**变更后检查清单**：
- [ ] DOCUMENTATION_MAP 已更新
- [ ] 全部引用已更新（grep 验证，0 真实断链）
- [ ] 涉及目录变更时 DIRECTORY_STRUCTURE 已更新、空目录已清
- [ ] 新增文件类型时 .gitignore 已检查
- [ ] commit message 记录了变更内容和联动动作
- [ ] 重要架构决策已记 ADR

### 5.3 文档健康度体检清单（大任务后/每月/用户要求时跑）

| 类别 | 检查项 | 方法 |
|------|--------|------|
| 完整性 | 所有文档在 DOCUMENTATION_MAP 有登记 | grep 文档名 |
| 完整性 | 新文档有类型标注（类型/更新频率/读者） | `head -10` |
| 关联性 | 链接有效、无文档孤岛（没被任何文档引用） | 链接检查 + `grep -r "文档名" --include="*.md" .` |
| 结构 | 目录与 DIRECTORY_STRUCTURE 一致、无空目录 | 对比 + `find . -type d -empty` |
| 结构 | 命名符合 NAMING_CONVENTION（类型↔风格一致） | 人工/脚本对照决策树 |
| 质量 | 无两文档讲同一件事的重叠 | 关键词搜索 + 人工审查 |
| 质量 | 无 >500 行且跨领域文档 | `wc -l` |
| 质量 | 无"正确的废话"、AI 套话、模板化表达 | 逐段看是否有独立信息增量 |
| 质量 | 术语一致、表述准确、结论有依据 | 与 ADR/规范对照 |
| 质量 | 无空标题/空章节（叶子标题下无正文） | 人工审查 |
| 维护 | .gitignore 合理（新文件类型已覆盖） | 审查 |
| 维护 | 核心文档（README/AGENTS/WORKFLOW/TASK_STATUS）与实际一致 | 对比现状 |

**问题分级处理**：小问题（断链、过时数字、漏登记、错字）当场修；
结构性/拿不准的（目录改名、文档拆分、流程/hook 变更）列方案先确认（L1/L2，见 [execution-ops.md](execution-ops.md) §一）；
用户要求"只读体检"则一律不改，只出报告。改后用不同方式复扫（重跑检查、断链扫描）确认无回退。

## 6. PROJECT_STATUS_QUERY.md 模板（项目状态查询协议）

> 解决"用户问得模糊、AI 凭记忆乱答"。规定：收到项目相关问题时先识别意图 → 读对应权威文档 → 按固定格式回答。
> 对长期由 AI 协作维护的项目特别有用；纯个人小项目可只保留意图表。

```markdown
# 项目状态查询协议

> 文档类型：Governance（AI 查询协议）
> 读者：AI 代理（收到项目相关查询时必须先参考）

## 一、查询意图分类
| ID | 意图 | 用户想知道 | 必读权威文档 |
|----|------|-----------|--------------|
| Q1 | 任务状态 | 还有哪些要做、进度、下一步 | TASK_STATUS.md |
| Q2 | 问题/缺陷 | 有什么问题/异常/风险/坑 | ISSUES.md |
| Q3 | 维护工作（只问清单） | 要做什么维护、有什么待优化 | 结构维护规范 + TASK_STATUS 待优化项 |
| Q4 | 文档/操作 | 某文档在哪、某操作怎么做、流程是什么 | DOCUMENTATION_MAP + WORKFLOW |
| Q5 | 项目概览 | 现在什么情况、总结一下、整体进度 | README + 00_项目总纲 + TASK_STATUS |
| Q6 | 决策/历史 | 为什么这样定、之前怎么处理的 | decisions/（ADR）+ 任务报告归档 |
| Q7 | 维护检查（执行型） | 让 AI 真去扫描/分级/修复/出报告 | 结构维护规范 + 本文 §5 体检清单 + DIRECTORY_STRUCTURE |

> Q3 与 Q7 的边界：只问"需要做什么维护"是 Q3（只读回答清单）；
> 带"检查/体检/维护一下/出报告"等动作词是 Q7（实际动手）。

## 二、模糊表达映射（说法不一时按此识别）
- Q1："还有什么要做的""做到哪了""下一步""待办""现在在做什么"
- Q2："有什么问题""有哪些 bug""有什么异常/坑/风险""哪里报错"
- Q3："需要做什么维护""有什么待优化/改进""定期检查什么""要清理什么"
- Q4："xx 文档在哪""怎么操作 xx""xx 流程是什么""有没有相关规范"
- Q5："项目现在什么情况""总结一下""整体进度""项目状态"
- Q6："为什么这样做""之前做了什么决定""历史记录""有哪些 ADR"
- Q7："给项目做个体检""维护一下项目""检查目录结构/文档规范""查断链/孤岛/冗余"

映射到多个意图或识别不出时：**不猜测**，给 2-3 个选项让用户选。

## 三、标准响应格式（按意图结构化回答）
- **Q1**：正在进行（任务/进度%/预计完成）→ 待开始（前置依赖）→ 最近完成（产出位置）→ 下一步。
- **Q2**：未解决（严重度/影响/状态）→ 最近解决 → 潜在风险。
- **Q3**：定期维护（周期/内容/检查方法）→ 待优化项（优先级/工作量）→ 最近完成的维护。
- **Q4**：直接相关文档（路径+一句说明）→ 操作步骤 → 注意事项。
- **Q5**：一句话目标 → 当前阶段/完成度 → 关键指标（来自现场复算，不凭记忆）→ 最近进展 → 下一步重点。
- **Q6**：相关 ADR（标题/状态/日期/背景/决策/后果）→ 相关历史报告 → 参考文档。
- **Q7（动手执行，不是回文本）**：
  1. 读 AGENTS/README/TASK_STATUS + 结构维护规范 + 体检清单 + DIRECTORY_STRUCTURE；
  2. 结构检查（文件归属、空目录、.gitignore、命名一致性，有脚本跑脚本）；
  3. 文档健康度按清单逐项扫，结论全部来自实际扫描/复算；
  4. 小问题直接修，结构性问题列方案先问；"只读"则一律不改；
  5. 改后复扫验证；按需出体检报告（过程件不入库）；同步 CHANGELOG/MAP/TASK_STATUS。

## 四、澄清话术
"我理解你可能想了解以下几个方面，请问优先看哪个？
1. 任务状态：还有哪些要做、当前进度；2. 问题缺陷：未解决的问题；3. 维护工作：待优化项与定期检查。"

## 五、维护
新增查询类型/发现新的模糊说法时，补进第一、二节；所有结论必须来自文档与现场核查，不凭对话记忆。
```

## 7. 质量验证规范与模板（QUALITY_ASSURANCE.md + VERIFICATION_TEMPLATE）

> 规定"各类产出物交付前怎么验证、谁是通过标准、问题怎么分级、验证怎么留痕"。
> 验证清单是项目特定的（每个项目按自己的产出物填 V1…Vn），本篇给框架和留痕纪律。

| 严重度 | 判定 | 处理 |
|--------|------|------|

| 中 | 不影响主流程但明显瑕疵 | 记录，本轮或下批修复 |
| 低 | 格式/个别小问题 | 记录，批量优化时处理 |

## 四、验证留痕原则（重要）
- **验证是必做动作，不是必交文档**：结论默认并入任务输出或《任务报告》（见 §9），
  不为每次验证单独生成"验证报告/同步报告"。
- 仅当验证对象非标准（专项质检）、或确需独立留痕时，才用 VERIFICATION_TEMPLATE，
  且只留本地、不对外同步。
- 能用接口返回/脚本结果客观判定的闭环（如平台返回状态、文件数对账、MD5 比对），
  以客观结果为准，不做主观重复验证。
- 验证通过后在 TASK_STATUS 对应工单标记"已验证"。

## 五、持续改进
验证中发现清单遗漏 → 立即补进本规范；高频验证步骤 → 沉淀为脚本；定期统计常见问题反哺生产流程。
```

## 8. 结构维护、文件去留与批量整改（PROJECT_STRUCTURE_MAINTENANCE 精华）

> 规范"文件该留还是该删、运行产物落在哪、怎么清理、批量改名/整改怎么走安全流程"。
> 存储分工总表见 [execution-ops.md](execution-ops.md) §四，本篇不重复，只管去留判据和整改流程。

### 8.1 写进规范的核心条款

```markdown
# 项目结构维护规范

> 文档类型：Governance ｜ 读者：AI 代理（项目维护时必须遵守）

## 一、结构维护原则
1. 仓库只放"怎么做"的工程资产（代码/文档/规范/模板/必要配置）；运行产物（环境、数据、日志、临时中转、缓存）落约定本地目录，由 .gitignore 忽略。
2. 脚本统一放 scripts/；文档按专业领域分目录；WORKFLOW 只留总体流程与索引。
3. 文件/目录有变化时强制检查 .gitignore；提交前 git status 确认无不该提交的文件；发现新文件类型及时补规则。
4. 定期清理测试文件、临时日志、残留目录，不堆积。

## 二、文件去留与沉淀判据（判断存量文档"保留/归档/沉淀/删除"）
> 第一判据是**对后续工作是否为必要输入**，不是"写都写了"的沉没成本，也不是篇幅长短。
1. **找不到任何具体使用场景、只是"也许以后有用"→ 归档**。归档用 git rm（文件在 git log/show 永久可取），不必为"以防万一"堆积。
2. **按性质分流，不一删了之**：
   - 一次性过程数据（报告、测试计划、整改清单、验证过程稿）→ 归档（过程件默认在 data/_workspace，本就不入库）；
   - 其中**可复用的结构**先抽成 templates/ 模板，再归档原件；
   - 稳定可复用的方法与规则 → 沉淀进对应规范，不留 在某份过程稿里。
3. **SSOT 去重**：一份文档的职责已被权威源全面承接 → 删除原件并级联清理所有引用，不在两处重复维护。
4. **历史轨迹不改写**：ADR、CHANGELOG、"已解决问题"记录保留当时事实与被否方案，价值在可追溯。
5. **判不准就高不就低**：拿不定留删时，先列"保留/归档/沉淀"清单及依据，按 L1 门禁确认后执行，不擅自删。

## 三、运行产物落点与忽略模式
| 产物类别 | 落点 | 入库？ |
|---|---|---|
| 依赖/虚拟环境（venv、node_modules、__pycache__） | 任意位置，靠依赖清单重建 | ❌ |
| 数据/抓包/原始素材 | data/（raw/processed/_workspace 分层） | ❌ |
| 运行日志/完成哨兵 | logs/、*.log、*.done | ❌（进度以正式台账为准） |
| 临时中转 | 系统临时目录或 .tmp_*/，脚本退出自清 | ❌ |
| 成品/代码/规范/模板/必要配置 | 正式目录 | ✅ |

两条硬规矩：
1. **两处同步**：新增一类运行产物，.gitignore 加规则的同时，（如有 pre-commit）把同名特征补进兜底拦截模式，互为备份。
2. **脚本自清**：临时中转目录用 `trap 'rm -rf "$tmp"' EXIT` 兜底；但**断点续跑凭证例外**（续跑要用的状态文件禁止 trap 删）。

## 四、清理方式（可恢复原则）
- 本地删除一律移废纸篓（带时间戳的批次目录），不 `rm -rf` 硬删；网盘/对象存储走回收站，删前先列目录取证。
- 同源重复件不能只凭文件名/大小判断，必须 MD5 或内容 diff 取证后再删。
- 替换类操作（如先补传新标准件再删旧件）保证任何时刻不缺内容。

## 五、测试/批处理闭环检查
多步骤任务在宣称"完成"前，按闭环清单逐项确认（前置→核心产出→质量验证→反馈/回写→文档同步→临时清理），
清单在开工前列进 TASK_STATUS，全部 ✅ 才能标完成；发现遗漏立即补做，不跳过。

## 六、批量重命名与结构整改 SOP（L1 高扩散变更，先方案后执行）
1. **问题调研**：按目录树逐文件检查，无问题也列，问题分类。
2. **先修依据**：命名/结构规则本身有矛盾时，先改 SSOT 规范并自洽复核。
3. **出整改方案**：老名/新名/依据/影响面（被哪些文件引用）四列全量清单（用 REFACTOR_PLAN_TEMPLATE）。
4. **用户确认（硬门）**：未确认不执行任何 git mv/删除。
5. **执行**：git mv 保留历史 + 全量级联更新引用/目录树/.gitignore。
6. **回归验证**：旧名活文档 0 残留、0 真实断链、类型↔命名 0 不自洽、目录树与实际一致、汇总数字由明细现算。
7. **记录收尾**：CHANGELOG 记一条，过程清单归档；本地改完待验收后再 push。
```
