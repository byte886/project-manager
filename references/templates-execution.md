# 执行模式模板（execution-patterns）

> 从真实项目提炼的执行期模板，适用于进入执行阶段的中大型项目。
> 生命周期类模板（目录/总纲/治理卡/ADR/台账/门决策/退役/关闭）见 [templates.md](templates.md)。

---

## 1. TASK_STATUS.md 模板（活跃任务台账）

```markdown
# 任务状态台账

> 本页是"当前做什么、到哪"的唯一进度真相，实时更新。
> 需求溯源看 docs/REQUIREMENTS.md，开放缺陷看 ISSUES.md。
> 稳定技术结论的权威版在 ADR / 工程记忆，本页只放指针、不复制结论。

## 依赖与并行前沿
- **阶段1**：✅ 完成（commit xxx）
- **阶段2**：⏳ 进行中
- **阶段3**：📋 待启动
- 可并行：A（后台运行）与 B（前台开发）可同时进行

## 工单清单

| 编号 | 标题 | 类型 | 前置 | 状态 | 验收 / 落点 |
|------|------|------|------|------|------------|
| T-01 | xxx | feature | 无 | done | 产出物路径 |
| T-02 | xxx | feature | T-01 | doing | 预期产出 |
| T-03 | xxx | bugfix | 无 | blocked | 阻塞原因 |
| T-04 | xxx | refactor | 无 | todo | 预期产出 |

状态四档：todo / doing / blocked / done

## 关键口径（指针，不展开）
- **技术点A**：结论一句话 → 见工程记忆 concepts/xxx
- **技术点B**：结论一句话 → 见 ADR-002

## 下一步（按优先级）
1. 最高优先级任务（T-xx）
2. 次优先级任务（T-xx）
3. 可后台运行的任务（T-xx）
```

## 6. 项目级 AGENTS.md 模板（AI 操作手册）

```markdown
# 项目 AGENTS.md（AI 操作手册）

> 本文件是给 AI 看的操作手册，命令式、可执行。
> 给人看的项目概览在 README.md，项目事实在 PROFILE.md。
> 与全局 AGENTS.md（`~/Doubao/AGENTS.md`）冲突时，本文件优先（仅本项目内）。
> 全局-项目协作关系详解见 initiate.md「项目创建后使用指南」第五章。

## 1. 项目定位与边界
- 做什么：一句话
- 不做什么：一句话（边界，防止范围膨胀）
- 当前阶段：调研期 / 开发期 / 运营期

## 2. 目录约定
- 什么东西放哪：列出关键目录（详见 docs/DIRECTORY_STRUCTURE.md）
- 路径规则：禁止硬编码 /Users/<用户名>，用 $HOME / 相对路径
- 六槽位（00/01/02/03/09/99）管项目治理，src/config/scripts/data 管工程，两者并存
- ADR 位置：统一在 <02_决策记录/ 或 docs/project-management/decisions/>，不要两处都放
- TASK_STATUS 位置：统一在 <03_进行中的任务/ 或 project-management/active/>

## 3. 数据约定（工程项目必看）
- `data/raw/` 是原始数据，**只读，绝不修改**；需要处理输出到 `data/processed/`
- `data/_workspace/` 是运行时过程件，**可随时清理**，不要把成品放这里
- `data/` 整体已 gitignore，不要尝试把数据文件提交到 git
- 数据文件命名：`<数据源>_<标的>_<时间范围>.<扩展名>`
- 大文件（>100MB）不入库，必要时用 Git LFS 或只存网盘

## 4. 凭证与安全（强制）
- API key、token、账号密码**绝不写进任何会入库的文件**
- 凭证放 `.secrets/`（加密 *.enc 可入库，明文已 gitignore）或环境变量
- 本地配置用 `config/local_*.py`（已 gitignore），不要修改 `config/default_*.py`
- 提交前必须 `git status` 检查，确认没有密钥/敏感信息

## 5. 工具用法与坑
- 本项目用什么工具、怎么调用、有什么坑
- 如：baostock 需先 login()；FunASR 首次下载模型需联网；每只股票下载间隔2-3秒防封

## 6. Git 工作流（工程项目）
- 分支：main（稳定）/ develop（开发）/ feature/<功能名>（功能分支）
- 提交信息格式：`<type>: <简短描述>`，type = feat/fix/docs/refactor/test/chore
- 调研期文档可直接提交 main；开发期功能开发走 feature 分支，合并前自测
- 每次提交前更新 TASK_STATUS.md，大变更写 ADR

## 7. 新会话恢复顺序
1. 读本文件（AGENTS.md）
2. 读 README.md（项目概览）
3. 读 PROFILE.md（技术栈/资源/约定）
4. 读 docs/DOCUMENTATION_MAP.md（文档地图，工程项目）
5. 读 docs/project-management/memory/index.md（工程记忆，如有）
6. 读 <03_进行中的任务/TASK_STATUS.md 或 project-management/active/TASK_STATUS.md>（当前进度）

## 8. 提交前检查
- [ ] 没有密钥/敏感信息入库（git status 确认）
- [ ] data/ 和 results/ 下的大文件未入库
- [ ] TASK_STATUS.md 已更新当前进度
- [ ] 新决策已写入 ADR
- [ ] 原始调研素材/数据未被修改
- [ ] （如启用文档同步清单）按 docs/project-management/standards/DOC_SYNC_CHECKLIST.md 跑一遍
```

## 10. WORKFLOW.md 模板（工作流总纲）

> 工作流是项目的"操作地图"：定义从开始到交付的阶段流水线、每个阶段的校验门（完成标准）、全局规则、以及各环节 SOP 的链接。
> 放 `docs/WORKFLOW.md`。**WORKFLOW 只放概览和校验门，不重复 SOP 的操作细节**——详细步骤在各 SOP 中，用链接指向。
> 设计要点（从高顿/内容流水线实采）：①文档边界表（明确本文档和其他文档的分工，不重复）；②阶段校验门（强制，每阶段完成必须通过才能进下一阶段）；③全局规则（跨阶段通用规则）；④SOP链接机制（WORKFLOW→SOP→工具脚本，三层不重复）。

```markdown
# 工作流 · <项目名>

> 文档类型：Workflow（工作流总纲）
> 更新频率：流程变更时
> 读者：AI代理（执行任务前必读）和人类（了解流程时）
> 最后更新：YYYY-MM-DD

> 本文档是项目的整体工作流，定义从开始到交付的阶段流水线及各阶段校验门。
> 各环节详细操作步骤见「参考文档」链接的 SOP，本文档只放概览和校验门，不重复细节。
```
