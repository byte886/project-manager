# L2 · initiate 项目启动（Initiation）

> 回答的问题：**"新项目怎么立项？目录怎么搭？写什么就算开工了？"**
> 对应专业方法：PMBOK 的 **Project Charter（项目章程）** 阶段——正式授权项目存在，写清目标、成功标准、边界。

## 启动到底在做什么

企业里项目启动要做两件事：
1. **写 Project Charter（项目章程）**：一页纸说清"为什么做、做成什么样算成功、谁负责、什么时候做完"。
2. **立项授权**：Sponsor 签字，项目正式存在。

个人场景没有 Sponsor 签字，但**Project Charter 不能省**——否则就是"脑子里有个想法"，不是"项目"。本技能把 Charter 具体化为「项目总纲一页纸」。

> 来源：PMI "Cancelling a Project Without Cancelling a Career" 强调没有 Charter 的项目最容易死 https://www.pmi.org/learning/library/cancelling-project-without-cancelling-career-5896

## 什么时候走本模块

- 脑子里冒出一个新方向，决定要认真做（不是顺手试试）。
- 想给已有但散落的资料（聊天记录、收藏夹、笔记）正式立一个项目空间。
- 反触发：一两天能做完、无长期归档需求的小任务，不必走本模块。

## 启动 SOP（步骤清单）

1. **先过 PPM 纪律**：到 [portfolio.md](portfolio.md) 看当前活跃项目数。若已 ≥ 7 个，先把低优先级的降到 On Hold，再开新坑——**活跃项目硬上限 7±2**。
2. **过 G1 立项门**：在 [gates.md](gates.md) 里过 G1——"这个项目值不值得做？"战略对齐 ≥ 3 分？没过就别启动。
3. **写一页"项目总纲"**（模板见下）：目标、截止日、成功标准（可量化）、当前状态、owner。写不出来 = 还没想清楚，先回到 idea-to-tickets 的 clarify 拷问。
   - **产品 / 业务 / 对外收费类项目，加写一页 BRD（商业需求文档）**：回答"为谁做、怎么赚钱、怎么算赢"，模板与边界见 [brd.md](brd.md)。Charter 管"项目怎么管"、BRD 管"生意成不成立"；BRD 最不确定的 3 条假设直接作为 G2 验证门判据。纯内部提效/学习/自用处可跳过 BRD。
4. **定状态标签**：新建项目默认 `Active`；还在调研、没真正开工的先标 `To Be Started`。
5. **按目录模板建结构**（见下），在飞书知识库或本地目录里落地。
6. **在项目台账里加一行**：项目名 / 状态 / 健康灯（新建默认绿）/ 战略对齐打分 / 资源占用预估 / 下次盘点日期。
7. **写一张治理卡**（见 [monitor.md](monitor.md)）：自己能拍板什么、什么情况必须暂停重评、多久碰一次。
8. **首条决策记录**：把"为什么做这个项目、放弃了什么备选"写进 `02_决策记录/`。

## 推荐目录模板（双层结构：项目管理层 + 工程扩展层）

> 所有项目都有**第一层（六槽位 + 标配文件）**；进入开发阶段的工程项目再加**第二层（工程扩展层）**。纯调研/文档型项目不需要第二层。

### 第一层：项目管理层（六槽位，所有项目必选）

```
📁 <项目名>/
├── 📄 00_项目总纲.md          ← 一页纸入口：目标/期限/成功标准/当前状态/owner
├── 📁 01_结论与产出/          ← 最终交付物（报告/方案/BRD/PRD）
├── 📁 02_决策记录/            ← 关键决策与理由（ADR）、治理卡
├── 📁 03_进行中的任务/        ← TASK_STATUS.md、ISSUES.md、进行中草稿
├── 📁 09_调研底稿与素材/      ← 原始资料、引用、截图、访谈记录、视频转写稿
└── 📄 99_复盘与退役总结.md    ← 完成后写（见 close 模块）
```

### 标配文件（所有项目必选，放根目录）

```
├── 📄 README.md               ← 项目概览，给人看（描述性：目标/架构/快速开始）
├── 📄 AGENTS.md               ← AI操作手册，命令式（指令性：目录约定/禁止事项/恢复顺序）
├── 📄 PROFILE.md              ← 项目事实层（稳定事实/技术栈/外部资源指针，易变状态不写）
└── 📄 .gitignore              ← 忽略规则（data/、results/、.secrets明文、venv、__pycache__等）
```

> README 给人看、AGENTS 给 AI 看、PROFILE 记事实，三者分离不重复。模板见 [templates.md](templates.md) 快速复制区。

### 第二层：工程扩展层（可选，进入开发阶段时启用）

```
├── 📁 src/                    ← 源代码（按模块分目录，如 data/features/strategies/backtest）
├── 📁 config/                 ← 配置文件；不入库的密钥用 config/local_*.py（已 gitignore）
├── 📁 scripts/                ← 可执行脚本（数据下载/批量处理/运维，snake_case命名）
├── 📁 tests/                  ← 测试
├── 📁 notebooks/              ← Jupyter研究（命名加日期前缀，如 2026-09-16_数据探查.ipynb）
├── 📁 data/                   ← 数据（整体 gitignore，不入库）
│   ├── raw/                   ← 原始数据（只读，绝不修改）
│   ├── processed/             ← 处理后数据
│   └── _workspace/            ← 运行时过程件（可随时清理，不传网盘/不同步）
├── 📁 results/                ← 回测/分析结果（gitignore，或只入库摘要报告）
├── 📁 docs/                   ← 工程文档（静态：方法论/规范/流程/模板/API）
│   ├── WORKFLOW.md            ← 工作流总纲（各环节SOP的入口和链接）
│   ├── REQUIREMENTS.md        ← 需求与验收标准（功能范围/验收标准/不做什么）
│   ├── DIRECTORY_STRUCTURE.md ← 目录结构详细说明（存储分工/各目录职责）
│   ├── DOCUMENTATION_MAP.md   ← 文档地图（所有文档的快速入口，先读这个）
│   └── project-management/
│       ├── decisions/         ← ADR决策记录（只增不改）
│       ├── memory/            ← 工程记忆（跨会话稳定结论，结论+指针）
│       └── standards/         ← 规范文档（命名/质量/编码/文档同步检查清单等）
├── 📁 .secrets/               ← 加密凭证（*.enc入库，明文*.json/*.txt已gitignore）
├── 📄 CHANGELOG.md            ← 变更日志（可选，中大型项目建议加）
└── 📄 LICENSE                 ← 开源协议（可选，公开仓建议加 MIT/Apache）
```

### 六槽位与 docs/project-management/ 的关系（不要并存造成混乱）

| 项目类型 | ADR放哪 | TASK_STATUS放哪 | 说明 |
|---|---|---|---|
| **轻量项目**（纯调研/文档，无代码） | `02_决策记录/` | `03_进行中的任务/` | 六槽位足够，不建 docs/ |
| **工程项目**（有代码/数据/脚本） | `docs/project-management/decisions/` | `project-management/active/` | 推荐统一到 docs/ 分层；02/03 可保留作为入口指针，或在 DIRECTORY_STRUCTURE.md 中说明已弃用 |

> **核心原则：选一种就统一，不要 ADR 同时出现在 02_决策记录/ 和 docs/project-management/decisions/。** 工程项目启用第二层后，建议把 02/03 里的内容迁移到 docs/project-management/ 和 project-management/active/，并在原位置留一个指针文件说明"已迁移至 xxx"。

### 为什么是这六个槽位（项目管理层）

| 槽位 | 作用 | 实证来源 |
|---|---|---|
| `00_项目总纲` | 入口页，30 秒看清项目是什么、到哪一步了 | 游戏项目「知识库总纲」、AI 情报站「阅读导航体系地图」 |
| `01_结论与产出` | 只放最终结论性文档，不和素材混 | 海口评估「01主报告·全景报告」 |
| `02_决策记录` | 记"为什么这么选"，半年后回看不后悔 | 对应 RACI/决策权限要求 |
| `03_进行中的任务` | 当前在做的事，一眼看到待办 | GTD 的 next actions 落地 |
| `09_调研底稿与素材` | 原始素材层，和结论分离 | 海口评估「03五份深度源报告（调研底稿）」 |
| `99_复盘与退役总结` | 完成后写，不提前建空文档也行 | SEO「数据复盘报告」 |

### 工程扩展层的设计依据（从高顿/内容流水线等成熟项目提炼）

- **data/ 三层分离**：raw（原始只读）/ processed（处理后）/ _workspace（运行时过程件），避免过程件污染成品
- **docs/ 双轨**：development（技术文档）+ project-management（治理文档：decisions/memory/standards），工程和治理分离
- **.secrets/ 加密凭证**：明文不入库，加密后的 *.enc 可入库，换机后解密即可
- **config/ 与代码分离**：配置集中管理，环境差异用 local_*.py 覆盖且不入库
- **project-management/active/**：活态台账（TASK_STATUS+ISSUES）独立于 docs/（静态文档），频繁更新的文件不混进静态文档区

## 从你飞书知识库提炼的五条结构规律

> 以下五条是从你现有 9 个知识空间实采归纳的，新项目直接照抄。

1. **数字前缀排序法**：凡是需要按顺序推进的内容，一律用 `NN_` 两位数字前缀（`01_`、`02_`…`06_`）。你已有实证：珠宝库 01–06、海口评估 01–03、CPA 章节 03–32。
2. **每个大空间必须有一个"总纲/导航"入口页**：根节点放一份 docx，写清"这个空间是什么、怎么读、当前到哪一步"。
3. **主报告 + 调研底稿分层**：结论性产出（01）和原始素材（09）分开，避免翻半天找不到结论。
4. **实践手册 / 技能 / 报告 三分离**：长期可复用的操作手册、可复用的自动化技能、单次产出的复盘报告，分开放。你已有实证：SEO 空间 = GA&GSC 实践手册 + 网站数据复盘技能 + 数据复盘报告。
5. **试点项打括号标记**：新尝试的方向用 `（试点）` 后缀，季度评审时优先回看。你已有实证：珠宝库「06 视频精解（试点）」。

## 飞书知识库创建操作指引

如果你决定把这个项目建成一个**独立飞书知识空间**（而不是塞进现有空间）：

1. 调用 **lark-wiki** 技能新建知识空间，命名 = 项目名。
2. 根节点放一份 docx，就是上面的「项目总纲」模板。
3. 按目录模板在根节点下建子节点（01_结论与产出、02_决策记录、03_进行中的任务、09_调研底稿与素材）。
4. 若需要多维表格做台账，调用 **lark-base** 建一张表（列定义见 [portfolio.md](portfolio.md)）。
5. 若是已有空间下的子项目，直接在该空间下建子树即可，不必新建空间。

> **股票投资若要作为项目管理**：首次实采时你的飞书 Wiki 空间里没有独立的股票知识空间（以现状为准），股票资料目前散落在多维表格或其他空间下。若决定把"股票投资"正式立为项目，可按本模板新建一个知识空间（如「股票投资组合」），把持仓、研究、复盘分桶；如果只是轻量记账，用 lark-base 多维表格做台账即可，不必建完整空间。

## 项目创建后使用指南（给后续 AI 会话看）

> **这是本技能最重要的一节**：创建项目不只是搭目录骨架，更是教后续每一个 AI 会话"怎么用这个项目、怎么扩展、怎么在框架内发挥"。
> 项目创建完成后，把本节要点内化到项目的 AGENTS.md 和 README.md 中，让新会话一进来就知道怎么干活。

### 一、每个文档是干什么的（文档角色表）

> 新会话先看这张表，知道每个文档的职责，不要读错文档、不要在错误的文档里找信息。

| 文档 | 给谁看 | 职责（一句话） | 什么时候读 | 怎么扩展 |
|---|---|---|---|---|
| **README.md** | 人 | 项目概览：目标/架构/快速开始/存储分工 | 第一次接触项目 | 项目目标/架构变更时更新 |
| **AGENTS.md** | AI | 操作手册：目录约定/禁止事项/恢复顺序/提交前检查（命令式） | AI 每次启动必读 | 规则/工具/目录变更时更新 |
| **PROFILE.md** | AI+人 | 事实层：技术栈/数据来源/外部资源/关键约定/已验证结论 | 新会话恢复事实时 | 稳定事实变更时更新 |
| **00_项目总纲.md** | 人+AI | 项目章程：目标/期限/成功标准/当前状态/治理卡指针 | 了解项目定位和进度 | 状态/里程碑变更时更新 |
| **docs/WORKFLOW.md** | AI | 工作流总纲：阶段流水线/校验门/全局规则/SOP链接 | 执行任务前 | 流程变更时更新 |
| **docs/REQUIREMENTS.md** | 人+AI | 需求唯一权威源：功能清单/验收标准/不做什么/开放问题 | 明确要做什么时 | 需求变更时更新 |
| **docs/DIRECTORY_STRUCTURE.md** | AI | 目录结构详细说明：存储分工/各目录职责/命名规则 | 不确定文件放哪时 | 目录变更时更新 |
| **docs/DOCUMENTATION_MAP.md** | AI+人 | 文档地图：按场景快速入口/文档完整清单/工具清单 | 找文档时 | 新增/删除文档时必须更新 |
| **TASK_STATUS.md** | AI+人 | 当前进度真相：做什么/到哪/下一步/工单清单 | 了解当前状态 | 任务开始/完成/遇阻时立即更新 |
| **ISSUES.md** | AI+人 | 问题清单：开放问题/已解决/Won't Fix（做不通的方向） | 遇到问题时 | 发现/解决问题时 |
| **ADR（决策记录）** | AI+人 | 关键决策和"为什么"，只增不改 | 做重要决策前查历史 | 关键决策时新增 |
| **工程记忆 memory/** | AI | 跨会话稳定结论（结论+指针，不复制原文） | 新会话恢复架构/链路时 | 稳定结论变更时更新 |
| **SOP（标准操作程序）** | AI | 重复性操作的标准化流程（前置检查/步骤/验证/断点续传） | 执行重复性操作时 | 操作步骤变更时更新 |
| **09_调研底稿与素材/** | 人+AI | 原始资料、转写稿、引用链接（只读，不修改） | 需要原始证据时 | 新增素材时加子目录 |

**文档分工三原则**（从高顿/内容流水线实采）：
1. **不重复**：每个信息只有一个权威源。如"需求"只在 REQUIREMENTS.md，WORKFLOW 不重复需求细节，只链接。
2. **按读者分**：README 给人看（描述性），AGENTS 给 AI 看（命令式），PROFILE 是事实（不写规则不写概览）。
3. **概览→详情分层**：WORKFLOW 只放阶段概览+校验门+SOP链接，详细操作在 SOP；DOCUMENTATION_MAP 只放入口，详细内容在各文档。

### 二、新会话读取顺序（冷启动 vs 续接）

> 同一项目，"第一次接触"和"接着上次做"读的文件不一样。判不准走冷启动（就高不就低）。

**路径 A · 冷启动**（首次接触 / 跨阶段切换 / 对任务归属没把握）：
1. 读 `AGENTS.md` — AI 操作规则（禁止事项、目录约定、恢复顺序）
2. 读 `README.md` — 项目概览（目标、架构、存储分工）
3. 读 `PROFILE.md` — 技术栈、数据来源、关键约定、已验证结论
4. 读 `00_项目总纲.md` — 项目目标、期限、当前状态
5. 读 `docs/DOCUMENTATION_MAP.md` — 文档地图（按需沿链接深读）
6. 读 `docs/WORKFLOW.md` — 工作流（了解整体流程和当前在哪个阶段）
7. 读 `TASK_STATUS.md` + `ISSUES.md` — 当前进度和开放问题
8. （工程项目）读 `docs/project-management/memory/index.md` — 工程记忆（稳定结论）

**路径 B · 续接**（用户说"继续/接着做 X"，仍是同一阶段同类活）：
1. 只读 `AGENTS.md`（扫规则）
2. 读 `TASK_STATUS.md` + `ISSUES.md`（到哪、下一步、卡在哪）
3. 读该环节那一篇 SOP + 上一单元样板成品
4. （需要时）读 `memory/index.md` 扫结论定位

> 判不准走 A 还是 B 时，**就高走 A**。多花 2 分钟读文档，比做错方向返工划算。

### 三、如何扩展项目（加新东西的规则）

项目不是一成不变的，随着推进会需要加新目录、新文档、新 SOP。扩展时遵守以下规则：

**加新目录**：
- 项目管理层（六槽位）不要随意加新槽位——00/01/02/03/09/99 已经覆盖了"总纲/产出/决策/任务/素材/复盘"的全生命周期。
- 工程扩展层可以按需要加子目录（如 `src/strategies/`、`data/raw/daily/`），但要在 `DIRECTORY_STRUCTURE.md` 中登记说明。
- 新增目录前先问：这个目录的内容能不能放进已有目录？能就不要新建。

**加新文档**：
- 新增文档必须在 `DOCUMENTATION_MAP.md` 中登记（按场景快速入口 + 文档完整清单两处都要加）。
- 文档命名：`<主题>_<类型>.md`，如 `数据下载_SOP.md`、`知识库组织方案.md`。
- 文档开头必须有元信息头：文档类型、更新频率、读者、最后更新日期。
- 不要创建"临时文档"——临时想法写进 TASK_STATUS 或 ISSUES，确认有长期价值再升级为正式文档。

**加新 SOP**：
- SOP 只用于**重复性操作**（每周/每天都要做的事）。一次性操作不需要 SOP，写进 TASK_STATUS 即可。
- SOP 命名：`<动作>_SOP.md`，放 `docs/` 根目录。
- SOP 必须在 WORKFLOW.md 对应阶段的"参考文档"中登记链接。
- SOP 模板见 templates-execution.md §8。

**加新 ADR**：
- 只有**影响架构/方向/重大取舍**的决策才写 ADR。日常小决定（如"这个函数用什么命名"）不写 ADR。
- ADR 只增不改，过时加"[已退役 YYYY-MM-DD：原因]"，不硬删。
- ADR 模板见 templates.md §4。

**文档演化与退役**：
- 项目推进会出现文档合并/退役（如内容流水线的原 PRD.md 合并进 REQUIREMENTS.md，原技术方案.md 被 DIRECTORY_STRUCTURE.md 替代）。
- 退役文档不要直接删除——在文档顶部加"[已退役 YYYY-MM-DD：内容已合并至 xxx.md]"，保留一个月后再清理。
- 退役原因写进 ADR 或 TASK_STATUS。

### 四、如何在框架内自由发挥（硬约束 vs 灵活调整）

> 框架是底线不是牢笼。以下是**硬约束**（不能违反）和**灵活区**（可以自由发挥）的划分。

**硬约束（必须遵守，违反会出问题）**：
- ❌ 不要把 API key、token、账号密码写进任何会入库的文件
- ❌ 不要修改 `09_调研底稿与素材/` 和 `data/raw/` 下的原始文件（只读）
- ❌ 不要在六槽位和 docs/project-management/ 两处同时放 ADR/TASK_STATUS（二选一统一）
- ❌ 不要跳过 WORKFLOW 的阶段校验门直接进入下一阶段
- ❌ 不要在调研期替用户决定框架选型/技术方向——只做对比，决策留给用户
- ❌ 不要删除用户已有的文件，覆盖前先确认
- ❌ 不要把 `data/` 和 `results/` 下的大文件提交到 git

**灵活区（可以自由发挥，框架不限制）**：
- ✅ 六槽位下的子目录可以自由组织（如 `09_调研底稿与素材/竞品视频/`、`09_调研底稿与素材/操盘手经验/`）
- ✅ 工程扩展层的目录结构可以按项目特点调整（如数据项目侧重 data/，Web 项目侧重 src/）
- ✅ SOP 的具体步骤和参数可以自由编写，只要符合 SOP 模板结构
- ✅ 策略/算法/方案的具体实现完全自由——框架只管"怎么组织项目"，不管"项目里做什么"
- ✅ 可以引入新工具、新框架、新数据源——只要在 PROFILE.md 登记、在 AGENTS.md 写明用法和坑
- ✅ 可以根据项目规模裁剪文档——小项目不需要全套 docs/，有 README+AGENTS+TASK_STATUS 就够
- ✅ 可以在框架内创建自定义文档类型——只要在 DOCUMENTATION_MAP 登记、写明用途

**一句话**：框架管"项目怎么组织、文档怎么协作、质量怎么保证"；不管"项目里做什么、怎么做、用什么技术做"。后者是你的自由发挥空间。

### 五、全局 AGENTS 与项目 AGENTS 的协作关系

> 新会话启动时，系统会先加载全局 `~/Doubao/AGENTS.md`，再加载项目根 `AGENTS.md`。两者是协作关系，不是替代关系。

| 维度 | 全局 AGENTS.md（`~/Doubao/AGENTS.md`） | 项目 AGENTS.md（项目根） |
|---|---|---|
| **管什么** | 跨项目的通用规则：搜索渠道偏好、回答引用规范、知识库归档路由、网络代理参数、自建技能清单 | 项目特有规则：目录约定、工具用法、禁止事项、数据约定、凭证规则、Git工作流 |
| **什么时候生效** | 所有项目、所有会话 | 仅在该项目目录下工作时 |
| **冲突时谁优先** | 兜底规则 | **项目 AGENTS > 全局 AGENTS**（仅该项目内） |
| **谁维护** | 全局规则变更时（如新增知识库空间、换代理） | 项目规则变更时（如新工具、新目录、新约定） |

**协作方式**：
1. 新会话启动时，系统自动加载全局 AGENTS（通用规则）。
2. 进入项目目录后，AI 应主动读取项目 AGENTS.md（项目特有规则）。
3. 项目 AGENTS 不需要重复全局 AGENTS 已有的规则——只写项目特有的。
4. 如果项目需要偏离全局规则（如"本项目不用飞书归档，用本地"），在项目 AGENTS 中明确写"覆盖全局规则第 X 条：本项目 xxx"。
5. 项目 AGENTS 的"新会话恢复顺序"中，第一步永远是"读本文件（AGENTS.md）"，因为项目规则优先于全局规则。

**项目 AGENTS 中应该写什么（不写什么）**：
- ✅ 写：项目特有目录约定、工具用法和坑、数据约定、凭证规则、禁止事项、提交前检查
- ❌ 不写：全局通用规则（如"引用要标注来源"——全局 AGENTS 已有）、项目概览（→README）、技术事实（→PROFILE）、需求细节（→REQUIREMENTS）

## 企业级重型 vs 个人轻量对照

| 主题 | 企业级重型 | 个人轻量（推荐你用） |
|---|---|---|
| 立项文件 | 完整 Project Charter（商业论证、范围、预算、干系人登记册） | 一页项目总纲（目标/成功标准/期限/owner） |
| 授权流程 | Sponsor 签字、PMO 备案 | 自己拍板 + 进项目台账 |
| 目录结构 | WBS（工作分解结构）到工作包级别 | 00/01/02/03/09/99 六槽位 |

## 反模式

- 立项时总纲写一大段愿景，没有可量化成功标准 → 半年后无法判断做完了没。
- 不数当前活跃项目数就开新坑 → 三个月后 12 个项目全部 On Track 但全部停在 30%。
- 把调研底稿和最终报告塞在同一个文件夹 → 找结论要翻 50 个文档。
- 目录建完后从不更新总纲 → 半年后自己都忘了这项目是干嘛的。
- 没过 G1 立项门就开工 → 做了两个月才发现战略对齐只有 2 分。
