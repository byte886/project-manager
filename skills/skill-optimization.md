# 技能类项目优化 SOP

> **文档类型**：Process（技能治理 — 编写与优化）
> **读者**：AI 代理 / 技能维护者
> **触发**：① 新建技能时；② 优化现有技能时；③ 整理技能目录结构时。
> 本文件规定**技能类项目的特殊规范**；通用项目规范（命名、文档写作、评审、结构维护）见 [`../standards/`](../standards/README.md)。

---

## 1. 核心原则：给AI用，不是给人看

技能文档的第一读者是AI，不是人。所有优化都围绕一个目标：**AI打开就能找到要找的东西，不用猜、不用读一大段才知道用什么**。

| 原则 | 说明 |
|---|---|
| **总纲不堆细节** | SKILL.md是导航，不是说明书；具体流程、参数、输出格式都指向references里的文档 |
| **指针优先，不重复** | 同一个内容只在一个地方写详细版，其他地方只放指针（链接+一句话说明） |
| **见名知意** | 文件名、目录名一看就知道是干嘛的，不用打开看内容 |
| **结构对称** | scripts和references的分类逻辑一致，AI知道"下载类的脚本在download/，对应的文档在platforms/" |

## 2. 技能标准目录结构

```
skill-name/
├── SKILL.md          # 总纲（导航，不堆细节）
├── scripts/          # 可执行脚本
├── references/       # 说明文档
└── README.md         # 技能简介（可选，SKILL.md已经够了可以不要）
```

### 2.1 scripts/ 按功能分类
```
scripts/
├── README.md         # 每个脚本的用途（按功能分组）
├── download/         # 下载类（从各平台下视频/音频）
├── process/          # 内容处理类（转写、OCR、抽帧、清洗）
├── cdp/             # CDP浏览器自动化类（提取流、处理弹窗）
└── live/            # 直播类（直播录制）
```

**分类规则**：
- 通用脚本（支持所有平台）放对应功能目录，不标平台
- 平台专用脚本放对应功能目录下的子目录（如`download/xiaohongshu/`）
- 底层工具（如点弹窗的脚本）放对应功能目录，备注"内部依赖，一般不直接调"

### 2.2 references/ 按功能分类
```
references/
├── README.md         # 每个文档的用途（按功能分组）
├── platforms/        # 平台相关（各平台策略、风控、专用方案）
├── process/          # 内容处理相关（转写、OCR、效果分析的详细说明）
├── pipeline/         # 流水线相关（完整SOP、编排方法）
└── domain-plugins/   # 行业插件（不同行业的知识提取模板）
```

**分类规则**：
- 和scripts/的分类逻辑对应：download/类脚本对应的平台文档放platforms/，process/类脚本对应的处理文档放process/
- 完整流程SOP（如作者全量知识库）放pipeline/
- 行业特定的模板（如珠宝、视频创作）放domain-plugins/

## 3. 技能类命名特殊规范

通用命名规范（snake_case、kebab-case）见 [naming-convention.md](../standards/naming-convention.md)，技能类额外加两条：

### 3.1 脚本文件名：带技术栈前缀
格式：`技术栈_功能.扩展名`（技术栈放前面，功能放后面）

| 好的命名 | 不好的命名 | 说明 |
|---|---|---|
| `funasr_transcribe.py` | `transcribe.py` | 一看就知道用FunASR转写 |
| `macos_vision_ocr_pipeline.py` | `video_ocr.py` | 一看就知道用macOS Vision做OCR |
| `opencv_keyframe_extractor.py` | `extract_keyframes.py` | 一看就知道用OpenCV抽帧 |

**规则**：
- 通用工具不用加技术栈（如`clean_subtitle.py`，纯文本处理）
- 平台专用脚本加平台名前缀（如`xiaohongshu_downloader.py`）

### 3.2 文档文件名：功能描述，见名知意
用小写+连字符（kebab-case），和通用规范一致。

## 4. SKILL.md 写法规范（总纲）

### 4.1 头部YAML
```yaml
---
name: skill-name
description: 一句话总览。支持平台/能力清单。核心能力1、核心能力2、核心能力3。特殊场景（必须用本技能的情况）。
compatibility: 仅 macOS 实测；Windows/Linux 未适配
---
```

**description的写法**：
- ✅ 写"能做什么"（功能清单）：支持YouTube/B站/抖音，核心能力：下载、转写、OCR
- ❌ 不写"怎么做的流程"：字幕优先→转写→OCR→成文（这些放正文）
- ✅ 写触发词：下载视频、视频转文字、批量下载
- ❌ 不重复写：把同一个意思说好几遍

### 4.2 正文结构（按顺序）
1. **大标题+一句话简介**：这个技能是干嘛的，指针指向详细内容
2. **执行原则**：AI必须知道的硬规矩（如"统一走外部Chrome"）
3. **脚本列表**：按功能分组（download/process），每个脚本一句话说明用途
4. **场景→服务映射表**：按用户需求选对应功能，AI一看就知道什么需求用什么
5. **核心流程详细说明**：比如出文章的六条决策顺序
6. **各平台关键策略表**：每个平台一行，关键坑+指针指向详细文档
7. **行业插件指针**：支持哪些行业，详细模板见domain-plugins/
8. **硬性约束与交付检查**：真正的硬规矩（不要改参数、日语要加--lang ja等）
9. **进阶场景指针**：如作者全量知识库、视频效果分析等，详细SOP指向文档

### 4.3 指针写法
```markdown
详细流程与输出模板见 [references/<对应文档>.md](references/<对应文档>.md)
```

**规则**：
- 每个指针都要有：链接+一句话说明这个文档是干嘛的
- 不要只放链接，不说明
- 同一个内容只在一个地方写详细版，其他地方只放指针

### 4.4 优化SKILL.md的步骤（从旧到新的改造流程）
适用于已经写了很久、内容堆砌、AI不好找的旧SKILL.md。

| 步骤 | 做什么 | 例子 |
|---|---|---|
| 1. **改头部description** | 从一大段改成功能清单+触发词，删掉具体流程 | 旧："字幕优先→转写→OCR→成文..." → 新："支持YouTube/B站/抖音，核心能力：下载、转写、OCR" |
| 2. **合并重复内容** | 原来可能有"什么时候用"、"三层架构"、"文件指引"三个重复部分，合并成一个场景→服务映射表 | 三个列表 → 一个表格，按功能分大类 |
| 3. **脚本列表按功能分组** | 原来一堆脚本平铺，现在按download/process/cdp/live分组，每个一句话说明 | 原来6个脚本平铺 → 分成下载类3个、处理类3个 |
| 4. **核心概念改成指针** | 原来写了一堆术语的大白话，现在改成一行指针，详细内容指向文档 | 原来12个术语各写一句 → 现在一行"术语详细见对应文档开头" |
| 5. **平台策略精简成表格** | 原来每个平台写一大段，现在每个平台一行，关键坑+指针 | 原来8个平台各写5行 → 现在8行表格 |
| 6. **删掉重复的执行原则** | 原来compatibility已经说了macOS only，正文又写一遍，删掉 | 正文里删"仅macOS可用"，只在头部YAML说一次 |
| 7. **统一指针式写法** | 所有详细内容都指向references里的文档，正文只留总纲和核心决策 | 原来大段抄文档内容 → 现在只放"详细见xxx.md" |

**优化前后对比**：
- 旧SKILL.md：140行，AI要翻一大段才知道用什么
- 新SKILL.md：80行，AI看表格直接定位，token省40%

### 5.1 scripts/README.md

## 6. 文档合并与优化手法

### 6.1 合并场景
- **方法论+模板型**：一篇讲原则、一篇给模板 → 合并为"原则在前、模板在后"
- **详略重复型**：两篇讲同一件事，一详一略 → 保留详版

### 6.2 合并步骤
1. 两篇各自先精简、去冗余
2. 按逻辑顺序合并：原则在前、模板在后；概念在前、示例在后
3. 删掉重复内容，同一意思只说一遍

### 6.3 合并标准
- 无冗余：同一内容不写两遍
- 结构清晰：先讲规矩、再给模板、最后给示例
- 文字精炼：每一句都有用，没有废话

## 10. SOP的标准结构（所有SOP文档都应该按这个写）

每个SOP文档（不管是技能SOP还是项目管理SOP）都应该包含以下7部分：

| 部分 | 作用 | 我们的对应 |
|---|---|---|
| **1. Purpose and Scope**（目的和范围） | 为什么有这个SOP、什么时候用 | 文件头部的"什么时候用" |
| **2. Roles and Responsibilities**（角色和职责） | 谁做什么 | （个人项目一般不需要，团队项目需要） |
| **3. Prerequisites**（前置条件） | 开始前要完成什么 | （可以加在"什么时候用"下面） |
| **4. Process Steps**（流程步骤） | 一步步怎么做 | 文件的主体内容 |
| **5. Success Criteria**（成功标准） | 怎么算做完了 | 文件头部的"达到什么效果" |
| **6. Escalation**（升级） | 出问题找谁 | （个人项目一般不需要） |
| **7. References**（参考） | 相关文档链接 | 文件里的指针链接 |
