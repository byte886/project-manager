# AGENTS.md · AI操作手册

> **什么时候用**：项目刚搭起来，要给AI立"宪法"时——新会话冷启动、跨阶段接手、换窗口继续干活，AI需要一份命令式手册告诉它"先读什么、红线是什么、什么不能做"。每个项目根目录只放一份。
> **怎么用**：先读下面的写作原则，再复制「模板本体」到项目根目录 `AGENTS.md`，把 `<>` 占位符全填了。
> **达到什么效果**：任何新AI窗口读完这一份 + 指的几份文件就能上手，不用翻聊天记录；规则命令式可执行，不用二次解释。

---

## 一、写作原则（先读这个）

### 1.1 非可推断测试（最重要）

对每条规则问自己：**"如果删除它，AI会犯错吗？"**
- 不会 → 删除
- 会 → 保留

应用后通常能消除 70–80% 本能想写的内容。

### 1.2 只写四类高价值内容

| 类别 | 说明 | 示例 |
|------|------|------|
| 精确的工具和版本 | AI无法可靠猜测的具体命令与版本号 | "Python 3.12, not 3.11"、"pnpm, not npm" |
| 逐字可执行命令 | 安装、测试、构建、部署的精确CLI字符串 | "Run `pnpm install --frozen-lockfile`" |
| 反直觉的约定 | 项目偏离默认值的地方 | 非标准目录布局、自定义错误处理模式 |
| 权限边界 | AI可以做什么、要确认什么、永远不能做什么 | "Never push to main directly" |

### 1.3 不应该包含的内容

| 内容类型 | 原因 | 处理方式 |
|----------|------|----------|
| README中已有的内容 | 冗余会降低任务成功率、增加推理成本 | 链接或引用，不重复 |
| 长篇架构解释 | 对人有用，对始终加载的上下文是负担 | 移到 references/，按需读取 |
| 详细API文档 | AI可以在需要时获取 | 链接到实际文档 |
| 标准语言/框架约定 | 已在模型训练数据里 | 不写（如"遵循PEP 8"） |
| 不言而喻的建议 | 不约束行为，只消耗上下文 | 删除（如"写干净的代码"） |
| 频繁变化的信息 | 应放工作记忆/会话提示 | 不写（如当前冲刺任务列表） |

### 1.4 篇幅控制

- 理想长度：**50–200行**；超过200行，边际指令开始互相竞争注意力
- 把根文件当**高密度摘要**，不当手册
- 长篇内容拆到 references/ 或 skills/，按需加载

## 2. 执行前必读：分「冷启动 / 续接」两条路径（强制）

先判断本次属于哪种，再按对应路径读；**不靠对话记忆猜测、不引用已废弃的旧路径 / 旧命令**。

### 路径A · 冷启动（满足任一即走A）

首次接触本项目 / 跨阶段切换 / 用户要求全面梳理 / 对当前任务归属或前置依赖没把握。按序读：

1. `<README.md路径>` — 项目概览、存储分工、常用命令
2. `<project-management/memory/index.md路径>` — 跨会话稳定结论与硬约束的"编译入口"
3. `<docs/REQUIREMENTS.md路径>` — 项目目标、功能范围、验收标准
4. `<docs/WORKFLOW.md路径>` 对应环节 → 沿其「参考文档」读专项SOP
5. `<project-management/active/TASK_STATUS.md路径>` + `<ISSUES.md路径>` — 当前状态、下一步、已知坑

### 路径B · 续接（用户说"继续 / 接手 / 接着做X"，且仍是同一阶段同类活）

只读：

1. `<memory/index.md路径>`（只扫结论定位）
2. `<TASK_STATUS.md路径>` + `<ISSUES.md路径>`（到哪、下一步、已知坑）
3. 当前任务的过程台账 `<workspace/<task>/路径>`（批次明细、断点、日志）
4. **当前环节那一篇SOP的相关小节 + 上一个样板成品**

**续接路径不全文读README / REQUIREMENTS / WORKFLOW**（冷启动已建立、记忆层与台账有指针），确有需要沿指针下钻单节。**判不准走A还是B时，就高走A。**

## 3. 核心规则（强制，必须遵守）

### 3.1 问题驱动更新

发现任何问题（文件位置不对、脚本报bug、流程有缺陷、文档缺失）时，必须立即评估是否需要更新文档或补检查项，评估后必须执行——不能只发现问题不更新。

### 3.2 按变更影响分级处理（先确认再执行）

- **L0顺手修复**：错字、单处断链、单文件明显小错、不牵动其他文件 → 直接修复并记一笔。
- **L1高扩散变更（必须先出方案、用户确认后才执行）**：批量重命名 / 跨目录移动、预计≥5处引用级联、修改命名或治理规范本身、新增或删除"持久文档 / 机制"。必须先给「方案 + 全量影响清单（老→新 / 依据 / 影响面）」，用户确认后再动手。
- **L2架构 / 流程变更**：流程变更、架构调整、新增技术选型 → 先和用户讨论，确认方案后再执行。
- 拿不准属于哪一级时，**就高不就低**，先按L1出方案。

### 3.3 写新文档前先查重（防重复建设）

遇到问题需要写 / 更新文档时，先查分工再落笔：

1. `ls <docs/目录>` 看现有结构；
2. `grep -rn "<关键词>" <docs/目录>` 查是否已有相关内容；
3. 新文档要承担的每项职责，逐一指认现有权威源；职责已被承担则**不新建**，改为在权威源里补内容。

### 3.4 大任务先建状态记录

开始大任务前必须先建执行状态记录；异常恢复时必须先读状态记录再动手。

**必须建记录的场景（满足任一）**：批量>3个 / 预计>1小时 / 涉及多工具链 / 用户明确要求"批量处理"。
**落点**：明细落过程工作区（不入库）；`TASK_STATUS.md` 只更新指针级状态，不抄批次明细。
详细规范 → `<project-management/standards/BATCH_TASK_EXECUTION.md路径>`。

**必须立即更新TASK_STATUS的时机**：任务开始 / 每个子任务完成 / 任务完成 / 遇阻塞 / 每次git提交前。

### 3.5 提交前体检

每次commit前逐项过：

- [ ] 进度数字只写在TASK_STATUS，别处没有第二份
- [ ] 新文档已登记进文档地图，没有"僵尸孤儿文件"
- [ ] 无凭证 / 密钥 / `.env` / 素材误入库（`git status`复核）
- [ ] 跑一遍构建 / 体检命令，0 ERROR
- [ ] 相关文档已按同步清单更新（指针 → `<standards/DOC_SYNC_CHECKLIST.md路径>`）

### 3.6 <项目专用强制规则，按需增删>

- <例如：包管理器用pnpm不用npm；Node版本锁定在.nvmrc>
- <例如：API key只进环境变量，绝不入库>

## 4. Things to Avoid（❌禁止 / ✅正确做法）

### 4.1 操作禁止

- ❌ <不要做什么，反直觉点写这里> — ✅ <正确做法>
- ❌ <不要做什么> — ✅ <正确做法>

### 4.2 文档禁止

- ❌ 不要把详细技术内容写进概览型文档（概览只放链接）
- ❌ 不要不查重就新建文档（见§3.3）
- ❌ 不要在多处抄同一份易变进度数字（只留TASK_STATUS一处真相）

- ❌ 不要不查文档就直接执行（先按§2路径读对应文档）

## 四、部署前检查清单

写完AGENTS.md后，逐项过：

1. 一个没有其他上下文的AI，仅凭本文件+代码库，能完成典型任务吗？
2. 每一行都通过非可推断测试吗——删除它会导致真正的错误吗？
3. 精确的版本、精确的命令、精确的权限都说明了吗？
4. 可信与不可信输入之间的信任边界明确吗？
5. "完成"标准是确定性和可检查的（脚本/模式/测试套件），不是期望性的吗？
6. 文件在~200行以内，还是额外内容已模块化到skills/references？
7. 文件中没有秘密、凭证或通过隐蔽性维持的安全措施吗？
8. 实际用AI在代表性任务上测试过吗？
