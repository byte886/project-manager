# 项目开头模板集

> 项目开头要写的文档模板，直接抄、填空就行。
> **不用全抄**，按下表根据项目规模和场景取用。

---

## 快速路由：你需要哪个模板

| 模板 | 解决什么问题 | 小项目 | 中项目 | 大项目 |
|---|---|---|---|---|
| **1. PRD 需求文档** | 要做什么、不做什么、验收标准 | ❌ 不用 | ✅ 建议 | ✅ 必须 |
| **2. BRD 商业论证** | 为谁做、怎么赚钱、值不值得 | ❌ 不用 | ⚠️ 商业项目用 | ✅ 商业项目必须 |
| **3. 系统要求与环境配置** | 换电脑怎么把环境跑起来 | ❌ 不用 | ✅ 建议 | ✅ 必须 |
| **4. 工作流程** | 整体怎么推进、分几阶段 | ❌ 不用 | ✅ 建议 | ✅ 必须 |
| **5. 目录结构** | 文件怎么组织、什么放哪 | ⚠️ 简单版 | ✅ 建议 | ✅ 必须 |
| **6. 文档地图** | 所有文档/命令的快速入口 | ❌ 不用 | ⚠️ 可选 | ✅ 必须 |
| **7. 项目管理README** | 治理文档的入口导航 | ❌ 不用 | ⚠️ 可选 | ✅ 建议 |

> **小项目**（1-2周，单线程）：README + AGENTS + 任务状态就够，不用本文件。
> **中项目**（1-3月，多任务/有代码）：按需选上面标✅的。
> **大项目**（3月+，多平台/批量处理/长期协作）：全套。

**原则**：规范是踩过坑后沉淀的，不是立项时拍脑袋写的。可以先建简单骨架，跑到需要时再补对应模板。

## 2. BRD 商业需求文档
> 什么时候用：要做个能赚钱的东西，先论证商业上值不值得做

# L2 · BRD 商业需求文档（Business Requirement Document，轻量版）

> 回答的问题：**"这件事在商业上为什么值得做？为谁做、怎么赚钱、怎么算赢？"**
> 对应专业方法：BA/产品体系的 BRD（Business Requirement Document），是 Project Charter 中"商业论证（Business Case）"的展开。

## 什么时候要写 BRD / 反触发

- **要写**：产品、业务线、创业、对外售卖/SaaS/服务、需要投入数周以上或真金白银、要说服合伙人/老板/客户/自己"这事值"的项目。
- **可不写**：纯内部提效工具、学习、内容整理、一两天的小任务、无商业交换的自用处——在项目总纲（Charter）里写一句"为什么做 + 成功标准"即可，不必套 BRD。
- **拿不准**：只要这个项目要"向外部收钱"或"赌上可观时间机会成本"，就写。

## BRD 与 Charter、PRD 的边界（别混写）

| 文档 | 回答 | 典型内容 | 读者 | 先后 |
|---|---|---|---|---|
| **Charter 项目总纲** | 这项目怎么立项、怎么管 | 目标、期限、成功标准、owner、治理 | 自己/协作人 | 最先 |
| **BRD 商业需求** | **为什么值得做、商业上怎么成立** | 客户、痛点、市场竞品、商业模式、定价、商业指标、Go/No-Go | 决策者/合伙人/老板/投资方 | Charter 后、PRD 前 |
| **PRD 产品需求** | 产品具体做成什么样 | 用户、场景、功能、流程、字段、规则、交互、验收 | 产品/研发/自己动手时 | BRD 验证后 |

一句话：**Charter 管"项目"，BRD 管"生意"，PRD 管"产品"。** BRD 不写功能字段细节（那是 PRD）；PRD 不重复论证生意成不成立（那是 BRD）。BRD 通过后，"接下来做什么功能"再交 idea-to-tickets 的 clarify→spec→slice 落成工单。

## 启动 SOP 中的位置

在 [initiate.md](../start/initiate.md) 写完项目总纲之后插入一个可选门：

1. 产品/业务/对外收费类项目 → 用下方模板写一页 BRD；
2. 把 BRD 里**最不确定的 3 条假设**拎出来，作为 **G2 验证门**的可测量判据；
3. BRD 结论为"商业不成立 / 关键假设证伪"→ Hold 或 Kill，不进入 PRD 与开发。

## BRD 轻量模板（一页到数页，按需取舍）

```markdown
# BRD · <项目/产品名> 商业需求文档
> 版本 v0.1 ｜ 日期 YYYY-MM-DD ｜  owner：<> ｜ 状态：草稿/评审中/已确认
> 配套：项目总纲(Charter) <链接>；本文件只讲商业，功能见后续 PRD。

## 1. 商业背景与机会（为什么是现在）
- 现状与变化：<政策/技术/市场/成本 发生了什么，使机会出现>
- 要解决的商业问题：<谁因为什么在损失钱/时间/机会，现在怎么凑合解决>
- 为什么我们能做：<我们独有的资质/数据/位置/渠道/成本/信任>

## 2. 目标客户与场景（为谁做）
- 首批客户画像：<行业/规模/地域/角色/决策人/付费人>
- 核心场景与痛点：<在什么场景、被什么卡住、频率、现在花多少代价>
- 付费意愿：<现在为这件事花多少钱/时间？谁出钱？预算从哪来>
- 不服务谁：<明确排除的客户，避免发散>

## 3. 市场与竞品（战场长什么样）
- 市场规模与结构：<TAM/SAM/SOM 或可触达客户数，注明口径与来源>
- 主要竞品/替代方案：<各是谁、怎么收费、强项弱项；含"人工现状"这个竞品>
- 我方差异化：<一句话定位；不与对手正面拼的维度、我们赢的维度>
- 进入策略：<从哪个细分/地域/尖刀场景切进去>

## 4. 商业目标与成功指标（怎么算赢，可量化）
- 北极星指标：<一个，如 付费客户数 / 经常性收入 / 单份交付成本>
- 阶段性指标（带时间）：
  - 验证期(G2)：<如 N 个真实意向/付费、X% 转化、可复现交付>
  - 成长期：<客户数/ARR/毛利/复购/人效>
- 止损线（No-Go）：<什么信号出现就停，如 3 个月 0 付费、单位经济为负>

## 5. 商业模式与盈利（怎么赚钱）
- 收费方式：<订阅/按份/项目制/License/分成/培训+实施/数据…>
- 定价与锚点：<价格区间、计费单位、对标谁、折扣策略>
- 单位经济：<单客售价 − 交付/算力/获客成本 = 毛利；回本周期>
- 成本结构：<固定（人/服务器/数据/凭证）+ 变动（Token/实施/售后）>
- 渠道与获客：<怎么触达首批客户、转化路径、客情/伙伴>

## 6. 解决方案概述与范围（高阶，不写功能细节）
- 我们提供什么：<产品/服务的一句话形态 + 3-5 个核心能力，不展开字段>
- 做什么 / 暂不做什么：<本期边界；明确不做的，防止膨胀>
- 关键依赖：<数据来源、资质牌照、第三方、合伙人、渠道>

## 7. 投入与资源
- 人力与分工：<谁出多少时间、需要补什么角色>
- 资金/工具/时间：<预算、订阅、关键设备；预计到达 G2/G3 的周期>
- 机会成本：<为此放弃了什么>

## 8. 风险与合规
- 商业风险：<获客不及预期、对手降价、客户不付费、依赖单点>
- 政策/法律/资质：<行业准入、签字责任、数据与个人信息、内容合规、版权>
- 缓解与预案：<每条主要风险一句对策；哪些是致命的>

## 9. 结论与 Go/No-Go
- 结论：Go / Conditional Go（带条件）/ Hold / Kill
- 进入下一阶段（PRD/开发）必须先验证的假设：
  | 关键假设 | 如何验证 | 可测量通过标准 | owner | 截止 |
  |---|---|---|---|---|
  | <客户愿付费> | <访谈/预售/MVP> | <> | <> | <> |

## 附：证据与未验证假设（诚实清单）
- 已核实事实：<>（带来源）
- 一方说法/宣传：<>（注明谁说的、待独立验证）
- 纯假设/估算：<>（标"假设"，不得当事实）
- 还缺什么数据：<>
```

## 写作要点（轻量但不省关键）

1. **客户与付费是 BRD 的心脏**：写不清"谁出钱、现在花多少、为什么改买你"，其余写再多也不通过。
2. **数字必须有口径**：市场规模、定价、成本、转化要么有来源，要么明确标"假设/估算"，不编精确数字撑场面（区分 事实 / 一方称 / 假设 / 待验证）。
3. **竞品要包含"人工现状"和"不做/Excel"**：小 B 市场最大的对手常常不是另一个软件，而是老办法。
4. **G2 判据前置**：BRD 的价值是在投入开发前，把"最怕错的假设"变成可证伪的小实验，而不是证明自己对。
5. **一页能说清就别写十页**：个人/小团队版聚焦第 2、4、5、9 节；其余从简。

## 反模式

- 把 BRD 写成功能清单（那是 PRD），却没回答谁付费、怎么赚钱。
- 用"市场巨大、前景广阔"代替可触达客户数与单位经济。
- 没有止损线，项目在"再试试"里无限烧时间。

## 方法来源

- BRD/MoSCoW、精益创业、Business Model Canvas、Phase-Gate 商业论证，均做了个人轻量化。

## 7. 项目管理README
> 什么时候用：项目开始建治理目录时

## 模板本体

```markdown
# Project Management — 项目治理体系

> 本目录是项目的**治理与过程管理层**，与 `docs/`（产品 / 技术文档）分离。
> 新会话启动时按根目录 `AGENTS.md` 的阅读路径，按本表路由读取对应文件。

## 目录结构

```text
project-management/
├── active/           # 活态台账（实时更新，唯一进度真相）
│   ├── TASK_STATUS.md    # 当前做什么、到哪了、下一步
│   ├── ISSUES.md         # 机制级坑 open→closed 台账
│   └── <task>.md         # 一次性专项任务的执行档案 / 交接书
├── decisions/        # ADR 架构决策记录（只增不改）
│   ├── ADR-001-<短标题>.md
│   └── ...
├── memory/           # 工程记忆 bundle（跨会话稳定结论编译层）
│   ├── index.md          # 记忆入口（新会话先读这里定位）
│   └── concepts/         # 各领域 concept（结论 + 指针，不复制正文）
├── reviews/          # 评审报告 / 阶段复盘
│   └── <YYYY-MM-DD>-<主题>-review.md
└── standards/        # 执行标准与规范
    └── <规范名>.md        # 如批量任务执行规范、文档同步检查清单
```

## 读取优先级

| 场景 | 先读 | 再读 |
|------|------|------|
| 新会话冷启动 | `memory/index.md` → `active/TASK_STATUS.md` | 对应 ADR / SOP |
| 续接任务 | `active/TASK_STATUS.md` → `active/ISSUES.md` | 该环节 SOP / 任务档案 |
| 做重要决策前 | `decisions/` 查历史 ADR（避免冲突） | 确认后写新 ADR |
| 大任务执行前 | `standards/` 找对应执行规范 | 再建执行状态记录 |
| 文档变更后 | `standards/` 找同步检查清单 | 逐项核对关联文档 |

## 维护原则

- **active/ 是唯一进度真相**：实时更新，不抄明细；别处不复制进度数字。
- **decisions/ 只增不改**：后来改主意不回头改旧 ADR，新建 ADR 说明演进，旧 ADR 末尾加"已于 ADR-NNN 被取代"。
- **memory/ 只放稳定结论**：结论 + 指针，不复制正文；易变值（进度、计数、当天日期）不进记忆层。
- **reviews/ 只在阶段结束做**：不随写随评；评审产出的改进项回到 active/ 工单跟踪。
```

## 什么时候**不**用这个模板

- 没有治理需求的小项目（单文件脚本 / 一次性 demo）——一个 README 就够，不用建五层目录
- 团队已有 issue / project 管理系统（Jira / GitHub Projects）——active/ 层指过去即可，不用在 markdown 里再造进度表
- 只想记决策、不想要完整治理——只建 `decisions/` 一层就够，别为了用模板而套全套
