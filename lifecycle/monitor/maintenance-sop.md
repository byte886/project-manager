# 项目维护SOP：一条信息只放一处

> **回答的问题**：项目跑起来后，怎么避免"同一条信息在好几个文档里，改的时候漏改、互相打架"？
> **什么时候用**：
> - 每次提交代码/文档前
> - 开新窗口、换AI接手时
> - 不确定"这条信息该写到哪"时
>
> **达到什么效果**：
> - 任何人/AI接手，都知道"这条信息去哪找、去哪写"
> - 新窗口不用翻旧聊天，看文档就知道项目情况
> - 提交前检查一遍，不会留下过时信息或漏登记

---

## 一、核心原则：一条信息只放一处

### 为什么要这样？

如果同一条信息（比如"项目目标是什么"、"当前进度如何"）在好几个文档里都写了：
- 改的时候很容易漏改某一处
- 时间久了，几个文档说法不一样，不知道哪个是对的
- 找信息要翻好几个文档，浪费时间

**解决方法**：
- 每类信息指定一个"唯一存放位置"
- 其他地方只放链接（指针），不复制内容
- 要改就改权威源，其他地方通过链接看到的永远是最新的

---

## 二、信息该放哪里（路由表）

> 这是核心表格，根据自己项目的实际文件路径填写。

| 信息类型 | 唯一存放位置（换成你项目的实际路径） | 其他地方只能 |
|---|---|---|
| 当前做什么、下一步、工单状态 | `任务状态文档`（比如 TASK_STATUS.md） | 放链接 |
| 已知问题、阻塞、踩过的坑 | `问题台账`（比如 ISSUES.md） | 放链接 |
| 一次性专项任务的档案 | `专项任务文档` | 台账登记一行 |
| 定了不改的重要决策（包括放弃的方案） | `决策记录`（ADR，只增不改） | 引用 |
| 跨会话稳定的结论 | `工程记忆目录`（有索引登记） | 引用 |
| 阶段复盘、评审报告 | `复盘目录` | - |
| 过程讨论：聊了什么→结论→为什么 | `交接日志`（HANDOFF，倒序追加） | 结论定稿后整理进决策记录/记忆 |
| 需求和功能范围 | `需求文档` | 放链接 |
| 整体工作流、阶段、检查点 | `工作流文档` | 放链接 |
| 长期规划、路线图 | `路线图文档` | - |
| 某个具体操作怎么做 | `操作指南/SOP目录` | 工作流放概览+链接 |
| 目录职责、存储分工、命名规则 | `目录结构说明` | - |
| 所有文档和脚本的索引 | `文档地图` | - |
| 容易变的数字（进度、当天日期、运行状态） | `台账/清单文件` | 其他地方不写死，只写"以台账为准" |

### 规则

1. **容易变的进度只留在台账**，其他地方不写死数字。
2. **过程讨论记在交接日志里**，定稿的结论必须整理进决策记录/工程记忆/SOP，不要在日志里长期堆结论。
3. **新增/移动/删除任何正式文档**，必须同步更新文档地图。

---

## 三、什么时候该做什么（维护节奏）

| 时机 | 必须做的事 |
|---|---|
| 完成一个子任务/里程碑 | 更新任务状态；重要讨论追加到交接日志；定稿结论整理进决策记录/记忆 |
| 遇到问题/阻塞 | 登记到问题台账，写清怎么复现、影响是什么；解决后更新，不删记录 |
| 准备提交（git commit） | 走下面的"提交前检查清单"，没有严重问题再提交 |
| 用户说"开新窗口/上下文太长了" | 走"新窗口接手流程"：老窗口收口 → 开新窗口 → 按六问验收 |
| 开始大任务（超过3个内容/超过1小时/多个工具） | 建执行状态记录（放在运行时工作区，不入库） |

---

## 四、提交前检查清单

每次提交前逐项检查：

- [ ] 容易变的进度只在台账里，其他地方没有写死的过时数字；交接日志已经追加了本轮重要决策
- [ ] 新增/移动的文档已经在文档地图登记；决策记录只增不改；空目录、空章节、没人用的脚本已经清理
- [ ] **没有密码、密钥、原始素材被误提交**（列出你项目禁止入库的东西：`凭证文件、大文件、API key...`）
- [ ] 运行了项目检查命令（如果有），**没有严重错误**（警告记录后可以提交）
- [ ] `git status` 看一下改动范围和本次意图一致；提交信息写清"做了什么、为什么"

## 五、新窗口接手验收（6个问题）

> 新会话**不翻旧聊天**，按照 AGENTS.md 里的冷启动顺序读完文档，应该能回答下面6个问题。
> 答不上来、或者文档自相矛盾，**先修文档再动手**（说明项目自描述有缺口）。

| # | 新窗口应该能回答 | 答案应该来自哪里 |
|---|---|---|
| ① | 项目是什么？主线是什么？现在在做哪些部分？ | 项目README、需求文档、关键决策记录 |
| ② | 做到哪了？最近完成了什么？ | 工作流文档、任务状态里的"最近完成" |
| ③ | 下一步做什么？哪些事等用户拍板？你的建议是什么？ | 任务状态里的"下一步/待拍板" |
| ④ | 有哪些开放问题、已知坑、数据缺口？ | 问题台账、各调研文档里的"坑/放弃项" |
| ⑤ | 红线是什么？哪些不能碰、哪些必须人工确认？ | AGENTS.md核心规则、各SOP硬约束 |
| ⑥ | 关键命令是什么？（启动、构建、测试、检查、git） | 各SOP快速参考、关键命令章节 |

```bash
# <写一行这个命令是干嘛的>
<命令>

# <写一行这个命令是干嘛的>
<命令>
```

## 七、诚实性原则

1. **数字、说法要有来源**：
   - "已验证/可行"必须有依据（实测记录、调研文档、台账）
   - 推测的要写"待验证/不确定"
   - 不要把某一方的说法直接当成确定结论

2. **走不通的死路要记录**：
   - 已经验证不行的方向，写进决策记录或调研文档的"放弃项"
   - 避免后来人重复试

3. **自动化检查能保证结构/链接/登记/不泄密**，但是**内容过不过时仍然要靠人/台账**，这是检查工具覆盖不到的。
