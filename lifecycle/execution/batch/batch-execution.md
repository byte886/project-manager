## 1. 什么时候必须建状态记录

满足任一条件，开工前必须先建状态记录：

1. 批量处理 >3 个项目
2. 预计执行时间 >1 小时
3. 涉及多个工具链（脚本 + API + 浏览器 + 构建等串联）

不满足以上三条的小任务（改 1-2 个文件、跑个单命令），不用建。

---

## 2. 状态记录落点

| 层级 | 位置 | 内容 |
|------|------|------|
| 批次明细 | `<workspace>/<batch_id>/`（不入库，加 .gitignore） | JSON 状态文件、锁文件、人读 markdown 记录 |
| 指针级状态 | `active/TASK_STATUS.md` | 只更新工单状态一句话 + 指向批次目录，不抄明细 |

**原则**：TASK_STATUS 是进度真相，但只放指针，不放批次明细。易变计数（已处理到第几项）只在批次 JSON 里。

---

## 3. 状态记录格式

### 3.1 批次状态文件（JSON）

路径：`<workspace>/<batch_id>/state.json`

```json
{
  "batch_id": "<batch_YYYYMMDD_NNN>",
  "status": "running",
  "total": <总数>,
  "completed": <已成功>,
  "failed": <失败数>,
  "current_item": "<当前正在处理的项名>",
  "failed_items": [
    {"name": "<失败项名>", "reason": "<失败原因一句话>"}
  ]
}
```

- `status` 取值：`running` | `completed` | `failed`
- 每处理一批（默认每 50 个）回写一次本文件

### 3.2 锁文件

- 位置：`<workspace>/<batch_id>/run.lock`
- 内容：当前进程 PID + 启动时间
- 作用：防止多进程同时跑同一个批次（新进程启动前先看锁文件在不在）
- **任务完成后必须删除**；异常中断后人工确认无残留进程再删

### 3.3 人读 markdown 记录（批次复杂时才写）

路径：`<workspace>/<batch_id>/RUN.md`

```markdown
# 批次执行记录：<batch_id>

> 启动：YYYY-MM-DD HH:MM
> 目标：<这个批次要干什么，一句话>

## 任务总览

| 指标 | 值 |
|------|-----|
| 总数 | <N> |
| 已完成 | <x> |
| 失败 | <y> |
| 当前项 | <当前在跑哪个> |
| 预计完成 | YYYY-MM-DD |

## 子项状态表

| # | 项名 | 状态 | 备注 |
|---|------|------|------|
| 1 | <项 1> | ✅ | |
| 2 | <项 2> | 🔄 | |
| 3 | <项 3> | ⏳ | |

状态标记：✅ 完成 | 🔄 进行中 | ⏳ 待启动 | ⚠️ 有问题 | ❌ 失败

## 问题记录表

| 时间 | 项 | 问题描述 | 严重程度 | 解决方案 | 状态 |
|------|----|----------|----------|----------|------|
| YYYY-MM-DD HH:MM | <项> | <现象> | 低/中/高 | <怎么处理的> | ✅ 已解决 |

## 恢复检查清单

- [ ] 读 `state.json` 确认进度
- [ ] 检查 `run.lock` 里的 PID 是否还活着
- [ ] 确认上一步输出完整（抽 1-2 个已完成项回读）
- [ ] 从 `current_item` 继续，不从头开始
```

---

## 4. 异常恢复流程

1. **查锁文件**：`cat run.lock` 看 PID；`ps -p <PID>` 确认进程是否还活着
   - PID 还活着 → 任务没挂，别重复启动
   - PID 不在了但锁文件还在 → 异常中断，进下一步
2. **读状态文件**：打开 `state.json`，跳过 `completed` 里的项，从 `current_item` 接着跑
3. **处理失败项**：`failed_items` 里的项重试，**最多 3 次**；3 次还失败就记原因跳过，别卡死
4. **删残留锁文件**：确认恢复前先把旧 `run.lock` 删掉再启动新进程

---

## 5. 必须立即更新 TASK_STATUS 的场景

1. 批次开始时（工单状态 → 进行中）
2. 批次完成时（工单状态 → 已完成，附产物路径）
3. 遇到阻塞 / 需要用户拍板时
4. 每次 git commit 前

---

## 6. 资源硬数字（不许拍脑袋）

| 项 | 上限 | 超过怎么办 |
|----|------|------------|
| 单批总数 | ≤500 | 超过就拆成多个批次跑 |
| 并发数 | ≤5 | 实测吞吐上不去就降，别加 |
| 状态保存频率 | 每 50 个存一次 | 量小就每完成一个存 |
| 失败重试次数 | ≤3 | 3 次失败记原因跳过，不无限重试 |

---

## 7. 进度偏差预警

| 预警 | 触发条件 | 处理动作 |
|------|----------|----------|
| 🟡 黄色 | 时间已用 60%，进度 <50% | 停下来重新评估剩余复杂度，看是不是预估错了或该优化流程 |
| 🔴 红色 | 时间已用 90%，进度 <80% | 申请额外资源（加并发/加人），或主动缩减非核心范围 |

---

## 8. 完成标准

- [ ] 总数 = 已完成 + 已跳过（失败项都有原因记录）
- [ ] `state.json` 已更新为 `completed`
- [ ] `run.lock` 锁文件已删除
- [ ] `active/TASK_STATUS.md` 已更新
- [ ] 按 `DOC_SYNC_CHECKLIST.md` 同步相关文档
```

## 什么时候**不**用这套规范

- 改 1-2 个文件、跑一条命令、写个小脚本——直接做，不用建状态文件
- 交互式短任务（问一句答一句那种）——没有"批量"概念
- 已经跑完的事——不用补记录，下次再跑时建

## 2. 并行调度与长任务守护
> 什么时候用：任务很大、要跑很久，怕中途断了

# 并行调度与长任务守护

> 解决执行期的两个高频问题：①多任务怎么拆、怎么定并发（不是拍脑袋并行）；②单次运行超过 AI 后台任务时限的活怎么"跑着不丢、完了主动通知"。
> 沉淀自真实批量流水线项目；方法论通用，示例中的工具可替换。

## 一、大任务先拆 DAG，再谈并行

任何多阶段大任务先完整拆解为子任务节点并标注依赖（有向无环图 DAG），**不拆清楚不要并行**。

### 1.1 三种依赖模式

| 模式 | 含义 | 示例 |
|------|------|------|
| **Linear Chain** | A→B→C 顺序依赖 | 下载→压缩→转写 |
| **Fan-Out** | 一个完成触发多个并行下游 | 下载完成→OCR + 压缩并行 |
| **Fan-In** | 多个上游全部完成才触发一个下游 | OCR+转写+采集→知识库生成 |

### 1.2 每个节点必须标注

任务名、依赖、预估时长、资源类型（CPU/IO/API/交互）、最优并发度、状态。

### 1.3 产出物

项目 `docs/development/project-dag.md`（或放 `03_进行中的任务/`）：一页 DAG，列出节点与依赖，供执行期对照。小项目可不落盘，但拆解动作不能省。

## 二、实测定并发，不凭核数估算

**并发数 ≠ 吞吐提升**，CPU 密集任务尤其如此——单进程速度必然随并发下降，总吞吐可能不升反降。

### 反向评估四步

1. **先跑单进程基线**：记录单进程 CPU 占用、内存、速度（rtf 等）、单任务耗时。
2. **逐步加并发**：从 2 开始每次 +1（或跳测 3/6），每个并发度稳定运行 ≥3 分钟再采样。
3. **对比总吞吐**：`总吞吐 = 并发数 × 单进程速度`；单进程速度必然下降，关键看总吞吐是否上升。
4. **选总吞吐最高的并发度**：串行最高就用串行（反直觉但常见）。

实测案例（FunASR 转写，14 核）：串行单进程 18.5x 速度 = 总吞吐 18.5x（最优）；并发 2 时总吞吐反而降到 11.8x——**串行就是最优**。不要被"多核就该并行"带偏。

IO/API 类任务并发收益更高，但仍要实测（限流、风控、排队都是约束）；外部 API 限并发、保序、失败隔离，用 `mapLimit` 类原语。

## 三、事件驱动衔接，总调度实时决策

- 阶段间**用"完成事件"触发下游**，不靠固定 sleep 轮询。
- 需要一个总调度者（人或 AI 主控）持有 DAG 视图，实时决定：哪些节点可并行启动、哪些要等、卡住的重试还是降级。
- 执行中的状态写进批次状态文件，调度读状态、不猜状态。

## 四、长任务守护范式（单次运行 > 8 分钟）

### 4.1 为什么不能直接后台跑

AI 工具的 `Bash(run_in_background=true)` 后台任务存在约 **8 分钟超时**，到点被杀。数小时的任务直接后台跑会被反复终止，AI 只能定期检查重启——这是"轮询"，消耗轮次且依赖 AI 在线。

### 4.2 守护器范式（推荐）

```text
nohup 守护器（PPID=1，系统 init 接管，AI 会话结束也不影响）
  └─ while 循环：
       1. 执行任务脚本（断点续传，done 标记跳过已完成项）
       2. 执行完成检测命令
          ├─ 全部完成 → 系统通知（macOS osascript / 其它平台对应）→ exit 0
          ├─ 连续 N 轮进度无变化 → 异常通知 → exit 1
          └─ 否则 sleep 5 秒，进入下一轮
```

要点：
- **任务脚本必须断点续传**（done 标记/状态文件），守护器只是循环调用，重复执行幂等。
- **完成判定用命令检测**（如 `grep 完成标记`、文件数对账），不用"感觉差不多"。
- 异常判定：连续 N 轮进度无变化视为卡死，主动通知并退出。
- 通知通道：macOS 系统通知（`osascript -e 'display notification ...'`）、飞书消息等；让 AI 不轮询也能知道结果。

### 4.3 分层清理孤儿进程

守护器/父脚本被杀后，子进程可能被系统收养继续跑。停任务须分层：先杀顶层脚本 → 按特征杀孤儿子进程 → 再杀最底层工作进程；用进程组 PGID 排除当前 shell，连续两轮计数 0 才算根除。
