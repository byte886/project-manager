## 1. 执行期治理骨架
> 什么时候用：换了新会话，AI不知道之前做到哪了

# 执行期治理骨架：工程记忆 / 活跃任务 / 项目级 AGENTS / 冷启动

> 项目已启动、进入执行阶段后"能跑起来"的轻量治理机制。本篇管**项目治理骨架**（记忆、任务台账、AI 操作手册、新会话怎么进）。
> 模式不是理论，从真实项目提炼。

---

## 〇、模式选用指南（先看这个，别一上来全搭）

| 项目规模 | 建议启用的模式 |
|----------|---------------|
| 小项目（1-2周，单线程） | TASK_STATUS + ISSUES 即可，其他可选 |
| 中项目（1-3月，多任务并行） | + 工程记忆 + 项目级 AGENTS + 文档同步清单 |
| 大项目（3月+，批量处理，多平台） | + 批量任务执行规范 + 存储分工/数据层编号 + 评审改进批次 |
| 所有项目 | 项目级 AGENTS.md（强烈建议，成本低收益高） |

**原则**：从 TASK_STATUS + ISSUES 开始，项目长大到需要时再加；每个模式启用时在 TASK_STATUS 记录"已启用 XX 模式"。

### 治理目录位置约定（六槽位 vs docs/ 分层，二选一统一）

项目治理文件（TASK_STATUS / ISSUES / ADR / 工程记忆 / 规范）有两种放法，**选一种就统一，不要并存**：

| 治理文件 | 轻量项目（六槽位） | 工程项目（docs/ 分层） |
|---|---|---|
| TASK_STATUS / ISSUES | `03_进行中的任务/` | `project-management/active/` |
| ADR 决策记录 | `02_决策记录/` | `docs/project-management/decisions/` |
| 工程记忆 | （可选，放 `02_决策记录/` 旁） | `docs/project-management/memory/` |
| 规范文档 | （可选，放 `02_决策记录/` 旁） | `docs/project-management/standards/` |
| 治理卡 | `02_决策记录/治理卡.md` | `02_决策记录/治理卡.md`（治理卡保留在六槽位，不迁移） |

**选择规则**：
- 纯调研/文档型项目、无代码 → 用六槽位，不建 docs/project-management/
- 有代码/数据/脚本的工程项目 → 推荐用 docs/ 分层；启用后把 02/03 里的内容迁移过去，原位置留指针文件说明"已迁移至 xxx"
- 治理卡始终在 `02_决策记录/治理卡.md`，不随 ADR 迁移

**为什么分两处**：六槽位是"项目管理层"（总纲/产出/决策/任务/素材/复盘），docs/ 是"工程文档层"（技术文档+治理文档）。工程项目文档多，按 development/project-management 分层更清晰；轻量项目文档少，六槽位足够。

## 一、工程记忆体系（project-memory bundle）

### 解决什么问题
每次新对话 AI 都要重新理解项目架构、踩过的坑、关键决策——重复问、重复查、容易遗漏。ADR 记录了"决策是什么"，但散落多处，新会话找不到入口。

### 怎么做
在项目 `docs/project-management/memory/` 下建轻量记忆 bundle：

```
docs/project-management/memory/
├── index.md              # 记忆入口（有什么、在哪、按领域分类）
└── concepts/             # 概念文档（每个是"结论+指针"，不复制原文）
    ├── architecture-xxx.md
    ├── workflow-xxx.md
    └── standard-xxx.md
```

### index.md 写法

```markdown
# 工程记忆 bundle

> 新会话恢复顺序：根 AGENTS.md（规则）→ 本页 index（有什么、在哪）
> → 按需沿每篇的「来源与下钻」深读原始文档。
> 本 bundle 只做"结论 + 指针"，不复制、不替代原文。
> 易变状态（进度、计数、当天日期）不进本 bundle，需要时实时读台账。

# 架构（Architecture）
* [架构名称](concepts/architecture-xxx.md) - 一句话说明（来源 ADR-xxx）

# 链路（Workflow）
* [链路名称](concepts/workflow-xxx.md) - 一句话说明

# 治理（Standard）
* [规则名称](concepts/standard-xxx.md) - 一句话说明
```

### concept 文档写法
每个 concept 50-150 行，结构固定：①一句话结论；②关键细节（3-5 条要点，带数字和做法）；③来源与下钻（指向 ADR/SOP/代码，不复制正文）；④常见坑（2-3 条）。

### 维护规则
- **只增不删**：过时加"[已退役 YYYY-MM-DD：原因]"，不硬删。
- **问题驱动更新**：发现记忆和实际不符当场更新。
- **不抄易变计数**：已完成多少以现场文件为准。
- **稳定结论指针化**：过程件只放指针指向 ADR/记忆，不复制正文。

## 二、活跃任务管理（active/）

### 解决什么问题
项目做着做着不知道"现在做到哪、下一步、卡在哪"。TODO 散落对话/脑子/便签，没有唯一真相源。

### 怎么做
在项目 `project-management/active/` 放两个动态文件：`TASK_STATUS.md`（当前做什么、到哪）+ `ISSUES.md`（开放/已解决/做不通的问题）。

### 维护规则
- **TASK_STATUS 立即更新**：任务开始/子任务完成/任务完成/遇阻塞/项目结构重大变更/每次 git 提交前。
- **ISSUES 发现即记录**：不等"攒够了再写"；解决后当场标注。
- **Won't Fix 很有价值**：记录"做不通的方向"，避免后来人重复踩坑。
- **不抄易变计数**：已完成多少以现场成品文件为准。

## 三、项目级 AGENTS.md（AI 操作手册）

### 解决什么问题
每个项目有自己的"怎么干活"规则（目录约定、工具用法、禁止事项），散在对话/README/脑子里。新会话 AI 容易犯"通用做法但本项目不行"的错。

### 怎么做
项目根目录放 `AGENTS.md`，与 `README.md` 分离：

| 文件 | 给谁看 | 写法 |
|------|--------|------|
| README.md | 人 | 项目概览、目标、架构、快速开始（描述性） |
| AGENTS.md | AI | 操作手册、命令式、可执行、禁止事项、路径约定（指令性） |

### 核心内容
①项目定位与边界；②目录约定（什么放哪、禁硬编码路径、用 `$HOME`/相对路径）；③工具用法与坑；④禁止事项（如"不要改 data/ 原始素材"）；⑤新会话恢复顺序；⑥提交前检查清单。

### 与全局 AGENTS.md 的关系
`~/Doubao/AGENTS.md` 是全局规则；项目根 `AGENTS.md` 是项目特有规则。冲突时**项目 AGENTS.md > 全局 AGENTS.md**（仅该项目内）。

## 四、冷启动 / 续接双路径（新会话怎么读项目）

> 同一项目，"第一次接触"和"接着上次做"读的文件不一样。判不准走 A。

### 路径 A · 冷启动（首次接触 / 跨阶段切换 / 对任务归属没把握）
1. 读 `README.md` — 项目概览
2. 读工程记忆 `memory/index.md` — 稳定结论定位
3. 读 `REQUIREMENTS.md` — 项目目标与验收标准
4. 读 `WORKFLOW.md` 对应环节 — 沿链接读专项 SOP
5. 读 `TASK_STATUS.md` + `ISSUES.md` — 当前状态

### 路径 B · 续接（用户说"继续/接着做 X"，仍是同一阶段同类活）
1. 只读 `memory/index.md`（扫结论定位）
2. 读 `TASK_STATUS.md` + `ISSUES.md`（到哪、下一步）
3. 读该环节那一篇 SOP + 上一单元样板成品

> 判不准走 A 还是 B 时，**就高走 A**。

### 交接（handoff）
要把项目交给新会话 / 另一台机 / 另一个 AI 时，写一份项目交接档，与"单会话单主题"纪律配套。

## 一、变更影响分级（强制：先确认再执行）

> 发现问题要改、或要动文件/规范前，先定级。**拿不准就高不就低**。

| 级别 | 定义 | 处理方式 |
|------|------|----------|
| **L0 顺手修复** | 错字、单处断链、单文件明显小错 | 直接修复并记录 |
| **L1 高扩散变更** | 批量重命名/跨目录移动、≥5 处引用级联、修改治理规范本身 | **先出方案 + 全量影响清单，确认后才执行**；本地改完先不 push，验收后提交 |
| **L2 架构/流程变更** | 流程变更、架构调整、新增功能 | 先和用户讨论，确认方案后再执行 |

> 拿不准属于哪一级时，**就高不就低**，先按 L1 出方案。

## 二、批量任务执行规范

### 解决什么问题
批量处理成百个同类项时，跑到一半崩了，不知道哪些做完、哪些失败、从哪续。没有断点续传，每次从头来。

### 触发条件（满足任一即建批次状态）
批量处理 >3 个同类项 / 预计 >1 小时 / 涉及多个工具链 / 用户明确要求"批量处理、全部完成"。

### 三层状态记录

| 层级 | 位置 | 内容 |
|------|------|------|
| 批次明细 | `workspace/state/` | 具体进度、断点、锁文件（不入库） |
| 指针级状态 | `project-management/active/TASK_STATUS.md` | 只更新工单状态，不抄批次明细 |
| 问题记录 | `project-management/active/ISSUES.md` | 机制级问题（换平台还会踩的） |

### 异常恢复流程
1. **中断检测**：锁文件存在但其中 PID 已不在 = 异常中断。
2. **恢复步骤**：读批次状态 → 从断点续（跳过已完成）→ 重试失败项（最多 3 次）→ 更新状态。
3. **紧急清理**：异常退出后清理残留锁文件和系统代理状态。

### 性能与资源保护
单批 ≤500 项（超过则分批）；下载并发 ≤5（避免触发风控）；资源密集型任务单进程；每 50 项存一次状态；失败项最多重试 3 次。

### 完成标准 Checklist
- [ ] 所有项处理完（总数 = 已完成 + 已跳过）
- [ ] 失败项有明确原因记录
- [ ] 状态文件更新为"完成"、锁文件已删
- [ ] TASK_STATUS.md 已更新、临时文件已清理
- [ ] 按文档同步检查清单同步相关文档

## 三、文档同步检查清单
> 什么时候用：每次commit前怕漏改关联文档

# 文档同步检查清单（DOC_SYNC_CHECKLIST）

> **什么时候用**：做完一批活、改了目录结构、解决了一个问题、或每次 `git commit` 前。核心场景是"代码/状态变了，但文档没跟上"——这个 checklist 强制你逐项核对哪些关联文档该同步。
> **怎么用**：把本文件放在 `project-management/standards/DOC_SYNC_CHECKLIST.md`。每次到了同步时机，打开本文件从上到下打勾。**不用单独填示例**——这本身就是个 checklist，照着勾就行；勾完发现某组一个都不用改，就整条跳过。
> **达到什么效果**：commit 之前一眼扫完"台账更了没、目录图更了没、MAP 更了没"，不会出现代码已经改了三周、文档还写着旧结构的脱节状态。

---

## 模板本体

```markdown
# 文档同步检查清单（DOC_SYNC_CHECKLIST）

> **文档类型**：Standard（规范 — 检查清单）
> **维护者**：AI 自动维护

---

## 1. 同步时机

遇到以下任一情况，必须跑一遍本 checklist：

1. 完成一批工作后（一个批次/一个阶段收尾）
2. 改了目录结构后（新增/删除/移动目录或文件）
3. 解决了一个问题后（新 ISSUE 关闭、bug 修完）
4. 每次 `git commit` 前

---

## 2. 检查清单

### 一、任务状态同步
- [ ] `active/TASK_STATUS.md` 已更新（工单状态、下一步、最近完成）
- [ ] `active/ISSUES.md` 已更新（新问题登记、已解决问题关闭但不删号）

### 二、文档关联同步
- [ ] `DOCUMENTATION_MAP.md` 已更新（本次新增/删除了哪些文档）
- [ ] `WORKFLOW.md` 已更新（如流程变了）
- [ ] `REQUIREMENTS.md` 已更新（如需求变了）
- [ ] `memory/index.md` 已更新（如有新稳定结论编译进来）

### 三、目录结构同步
- [ ] `DIRECTORY_STRUCTURE.md` 已更新（如目录树变了）
- [ ] `.gitignore` 已检查（新增的过程件/产物目录有没有忽略）
- [ ] `git status` 复核：确认没有不该入库的文件被 staged

### 四、工具与脚本同步
- [ ] 新增脚本已入 `DOCUMENTATION_MAP` 工具清单
- [ ] 删除脚本已从所有文档中移除引用（包括 README、SOP、AGENTS.md）

---

## 3. 快速检查命令

```bash
# 看一眼当前有什么改动
git status

# 扫一遍有没有遗留 TODO / 待补充
grep -r "TODO\|待补充\|待完善" . --include="*.md"

# 找空目录（建了忘了删/忘了放东西）
find . -type d -empty -not -path "./.git/*"
```

---

## 4. 核心原则

1. **问题驱动更新**：发现问题/做完东西，先想"这事影响到哪些文档"，别等 review 才补
2. **不抄易变计数**：别在多个文件里写死"共 200 本书""已完成 150 个"——计数只在台账/JSON 状态文件里，别处只放指针
3. **提交前必查**：每次 `git commit` 前至少过一遍 §2 的一、三两组（状态 + 目录），其余两组按需
```

## 四、存储分工硬约束

### 四地分工

| 位置 | 放什么 | 不放什么 |
|------|--------|----------|
| **Git 公有仓** | 代码、docs/、知识成品（清洗后）、台账元数据、ADR/工程记忆 | 媒体文件（视频/音频）、逐字转写稿、原文、凭证、过程件、临时文件 |
| **本地项目目录** | 原始资源 + 知识成品（唯一权威源） | — |
| **网盘/对象存储** | 成品镜像（备份） | 过程件、临时文件 |
| **飞书等协作平台** | 只发成品（不发过程件和原始素材） | — |

### 硬规则
1. **git status 是红线**：视频/音频/转写稿/凭证绝对不能进 git。
2. **本地是唯一权威源**：网盘和协作平台只是镜像/分发，本地丢了才真丢。
3. **知识成品才入库**：只有"自己话重组、带来源、清洗后"的成品才进 git；原始素材只在本地。
4. **凭证单独管理**：`.secrets/` 必须在 .gitignore，加密存储不入库。

## 五、数据层编号体系（内容类项目，可选）

### 解决什么问题
素材库目录乱——原片和成品混在一起，新会话不知道"处理到哪步"。

### 按处理阶段编号

```
library/
├── 00_manifest/        # 台账（manifest、水位、队列、批次状态）
├── 01_raw/             # 原始素材（按平台/账号分目录，不入库）
├── 02_middle/         # 中间件（如音频，过程件）
├── 05_knowledge/       # 知识成品（清洗后，入库）
│   └── concepts/       # 按内容类型再分（笔记/报告/方法/主题融合页）
└── 08_sources/         # 平台无关外部源
```

### 编号原则
- **数字前缀 = 处理阶段**，跳号留扩展空间（03/04 留空）。
- **原料 vs 成品**：01/02 原料不进 git，05 成品进 git，00 台账元数据进 git。
- **按来源/账号分子目录**。

> 编号只是约定，项目不涉及内容流水线时不必套用；按本项目实际阶段增减。

## 六、评审改进批次机制

### 解决什么问题
评审发现 20 个问题，一股脑全改容易乱、漏、不知道改到哪。按优先级分批，每批一个工单。

```
评审 → 问题清单（P0/P1/P2/P3）
     → 批次1(P0) → 工单 → 完成 → commit
     → 批次2(P1) → 工单 → 完成 → commit ...
```

### 批次记录（写进 TASK_STATUS.md）

| 批次 | 工单 | 内容 | 优先级 | 完成 commit |
|------|------|------|:---:|:---:|
| 批次1 | T-xx | <做了什么> | P0 | `<短hash>` |

### 评审核心结论（评审文档末尾必记）
总体评分、方向判断、最需改进的 3-5 个问题、按优先级分的批次清单。

## 七、项目治理工作什么时候并行 / 委托多智能体

> 季度盘点、批量评审、批量处理这类活，串行做又慢、又容易把前面细节挤出上下文。满足条件时可委托 AI 助手的**多智能体编排能力（OrganizerAgent，只点能力名、触发以助手为准）**切成独立子任务并行。本节只给项目管理视角的"什么活适合并行"，不复述平台的委托阈值。

### 适合并行（能切成彼此独立、各自闭环的单元）
- **季度批量评审多个彼此独立的项目**：每个项目独立走一遍门评审清单（见 gates.md），最后主控汇总。
- **多渠道 / 多平台调研**：官方、媒体、学术、本机数据等不同信源族各自检索取证。
- **≥3 个候选方案 / 平台 / 场景的横向对比**：每个候选独立成篇。
- **大量独立条目的批量处理**：批量采集 / 转写 / 校验，配合 §二断点续传。
- **单上下文装不下的资源密集语料**：按可独立验收的分片切。

### 必须自己连贯做、不要并行
- 强前后依赖、需要全局连贯推理：**定组合优先级、Go/Kill 最终拍板、写项目总纲、定治理卡阈值**。
- 子任务共享可变状态、边界切不清的。

### 切分与汇总纪律
1. **按"独立闭环单元"切，不按"步骤"切**：每个单元能独立完成 读取 → 处理 → 自检，不等别的单元的中间结果。
2. **统一口径 + 写入面隔离**：所有单元用相同的输出 schema、模板、评分口径与硬红线；子单元只写各自范围，不碰共享区和他人范围。
3. **主控负责对账**：去重、核对口径一致、交叉验证、汇总结论；并行只加速"信息准备与独立分析"，不代替最终判断。
4. **交接即冷启动**：给每个子任务附交接档，写清读取路径、验收标准、边界；产出回收后由主控统一落库。

> 一句话：**可独立验收的"平行分析/体力活"并行，需要价值判断和全局取舍的"决策活"留给自己。**
